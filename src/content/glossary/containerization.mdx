Containerization is how you package an application so it runs the same way on a laptop, in CI, and on a server. You build an image that holds the application and the libraries it needs. A host runs that image as a container. The container uses the host kernel instead of booting its own operating system.

That is the whole distinction from a virtual machine. A virtual machine carries a guest kernel. A container does not.

## What containerization is

You start from a base image, add your application, and set the command that starts the process. The result is an image, a file you can push to a registry and pull on another machine. Starting the image creates a container: a running process with its own filesystem view, its own network namespace, and limits on CPU and memory.

Stop the container and the process is gone. The image is still there, so you can start another copy. Anything the process wrote in the container's writable layer goes with it, unless you mounted a volume.

## Containerization and virtual machines

Teams pick containerization when a virtual machine is too much machine for one service.

|                     | Container                             | Virtual machine                  |
| ------------------- | ------------------------------------- | -------------------------------- |
| Isolation           | Processes on a shared kernel          | A guest kernel and a full OS    |
| What you copy       | An image of the app and its libraries | A disk image that includes an OS |
| Startup             | Usually under a few seconds           | Often tens of seconds or longer  |
| Density on one host | Many                                  | Fewer                            |

A container is a weaker security boundary than a virtual machine, because the kernel is shared. If you need a hard separation between tenants, use a VM, or run the container inside one. For services that already trust the host, the shared kernel is why containers start fast and pack tightly.

## Images, registries, and the running container

The image is the artifact. The container is the process. A registry such as Docker Hub, GitHub Container Registry, or a private registry holds the image between the build and the host that runs it.

A Dockerfile is the usual recipe:

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
USER node
CMD ["node", "server.js"]
```

`docker build` turns that file into an image. `docker run` starts a container from it. Other tools can build and run the same image. The [Open Container Initiative](https://opencontainers.org/) specifies the image format and the runtime, so the image is not tied to one vendor's builder.

Put the application in the container, not a pile of unrelated daemons. One process per container keeps restarts and logs obvious. The process should exit on SIGTERM, so a replacement can start without waiting out a kill timeout.

## Docker and Kubernetes

Docker made the workflow ordinary: a file in the repo, an image, a registry, a running container. Kubernetes and the schedulers built into hosting platforms do the next job. They place copies of the container on machines, restart a copy that dies, and send traffic to the ones that are up.

Containerization is the packaging. Orchestration is the scheduling. You can containerize an API and run a single copy with Docker, or with a host's own runner, and never set up a cluster.

## Containerization for APIs

An API fits this model because the thing you want to reproduce is specific: this process, these libraries, this port. The image that passed CI is the image production runs. You scale by starting more copies. That stays simple when the process keeps state in a database or another service, not on the container's own disk.

[Unkey Compute](https://www.unkey.com/docs/compute/get-started/deploy-an-image) runs that kind of API from a GitHub repository or from an image you already built. The process stays up and listens on a port. A gateway in front of it can check keys and apply rate limits. That is separate from how the container is built.

## What containerization does not do

It does not pick a host, store your data, or decide who may call the API. A container will run a broken build just as readily as a good one. Pin the base image, rebuild when it changes, and keep secrets out of the image layers. Pass them in when the container starts.

If two services need different kernels, or you do not trust them to share one, skip the container and use a virtual machine.
