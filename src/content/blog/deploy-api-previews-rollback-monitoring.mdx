# Deploy an API with preview environments, instant rollback, and request logs

To ship a public API you usually end up stitching four pieces together. You need somewhere to host it, a preview for each pull request, auth and rate limiting in front of it, and logs for when something breaks. On top of that you need a plan for rolling back on the day a release goes bad.

This post does all of it on Unkey. We deploy your API with Compute, issue and check keys with API Management, and record every request your app serves. I ran every command below against a real workspace, and the output is exactly what came back, with keys redacted.

## What you'll have at the end

By the end you'll have a production URL on `unkey.app` that updates every time you push to your default branch, and a preview for every other branch and fork PR. The gateway will check API keys and rate limit each caller. You'll get logs and metrics without installing an SDK, and you'll be able to roll back with one call and no restarts.

Before the first deploy you need a Compute plan. The dashboard asks you to **Choose a Compute plan**, and only a workspace admin can pick one.

## The sample API

Any language works as long as the container listens on `PORT`, which Unkey sets to the configured port (8080 by default). This is a minimal Hono app.

{/* prettier-ignore */}
```js
// index.js
import { Hono } from "hono";
import { serve } from "@hono/node-server";

const app = new Hono();

app.get("/healthz", (c) => c.text("ok"));

app.get("/v1/hello", (c) => {
  // Set by the gateway after a key-auth policy verifies the caller.
  const raw = c.req.header("x-unkey-principal");
  const principal = raw ? JSON.parse(raw) : null;
  return c.json({
    hello: principal?.subject ?? "anonymous",
    deployment: process.env.UNKEY_DEPLOYMENT_ID ?? "local",
  });
});

const port = Number(process.env.PORT ?? 8080);
serve({ fetch: app.fetch, port });
console.log(`listening on ${port}`);
```

Running it locally, with and without a principal header, looks like this.

```
$ curl -s localhost:8080/v1/hello
{"hello":"anonymous","deployment":"local"}
$ curl -s localhost:8080/v1/hello -H 'X-Unkey-Principal: {"version":"v1","subject":"acme","type":"API_KEY","source":{"key":{"keyId":"key_123","keySpaceId":"ks_123","meta":{}}}}'
{"hello":"acme","deployment":"local"}
```

Unkey injects `UNKEY_DEPLOYMENT_ID` into every instance, which helps during a rollback because you can see which deployment answered.

For the real runs I deployed a public echo server (`ealen/echo-server`) instead. It prints every header and variable it receives, so you can see the gateway's principal header and which deployment answered.

## Step 1: Connect the repository and deploy

### From the dashboard (GitHub)

1. Open **Projects** and choose **Create project**, then enter a **Project Name**. The **Slug** is generated from the name, and it's what the API and CLI use. The new project opens on an empty Apps list.
2. Choose **Create app**, set an **App Name** and **Slug**, and pick **Import from GitHub**. The first time you do this in a workspace, GitHub asks you to install the Unkey GitHub App and grant it repository access. After that, pick the repository under **Select a repository**.
3. Review **Configure deployment**. The defaults work for most repositories, with root directory `.`, the Dockerfile auto-detected (or pick your own), no watch paths, and auto deploy on for production and preview. For a monorepo, point the root directory at the service and add watch paths like `services/api/**` so pushes that don't touch it are `skipped`.
4. If you need environment variables, add them here, scoped per environment. Sensitive ones are write-only.
5. Choose **Deploy**.

### From the API or CLI

Every endpoint is a `POST` to `https://api.unkey.com/v2/{service}.{procedure}` with a root key in `Authorization: Bearer`. Start by creating the project.

```
$ curl -s -X POST https://api.unkey.com/v2/projects.createProject \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{"name":"blog-draft-payments","slug":"blog-draft-payments"}'
{"data":{"id":"proj_VuYAqnGfO"},"meta":{"requestId":"req_LouXFD59b"}}
```

For a GitHub repository, install the GitHub App with `github.installApp`, which returns a URL for you to open, and then create the app with `git.repository`.

```bash
# UNVERIFIED: not run for this draft (we connected GitHub through the dashboard instead)
unkey api apps create-app --project=payments --name='Payments API' --slug=api \
  --git='{"repository":"acme/payments","defaultBranch":"main"}'
```

If you already build images in CI, you can create the app from an image instead. That's the path I ran.

```
$ unkey api apps create-app --project=blog-draft-payments --name="Payments API" --slug=api \
    --oci='{"image":"ealen/echo-server:0.9.2"}'

$ unkey api deployments create-deployment --project=blog-draft-payments --app=api \
    --environment=production --oci='{"image":"ealen/echo-server:0.9.2"}' --output json
{
  "meta": { "requestId": "req_95uq5YVND" },
  "data": { "deploymentId": "d_GjCkWjVim" }
}
```

`create-deployment` returns right away, so you poll `get-deployment` until the status is `ready`, `failed`, `skipped`, `superseded`, `stopped` or `cancelled`.

![Terminal: create a production deployment, poll it to ready, and read its domains](/images/blog-images/deploy-api-previews-rollback-monitoring/01-deploy-ready.png)

The live production domain always follows the pattern `<project>-<app>-<workspace>.unkey.app`. You also get one domain for the environment and one pinned to the exact deployment (`...-d-gjckwjvim-...`), which is handy for testing a specific build.

A workspace runs one deployment at a time, from build through rollout, and the rest wait in `pending`. Production deployments jump the queue, so a hot fix never sits behind PR builds.

Behind the scenes the CLI calls `POST /v3/deployments.createDeployment` with an `oci` source. The older `/v2/deployments.createDeployment` still accepts `image.dockerImage`, but it's deprecated.

## Step 2: Every branch and pull request gets a preview

Once the repository is connected, you don't set anything else up for previews. A push to the default branch deploys production, and a push to any other branch creates a preview with its own branch domain. Each one shows up in GitHub as a GitHub Deployment, and Unkey keeps a single PR comment updated with a **Visit Preview** link.

Fork PRs work differently, because a fork's code would run with your preview variables, including database URLs, third-party API keys and anything else you put there. For an API that's a real risk, so a fork PR never builds on its own. It waits in `awaiting_approval` behind a failing **Unkey Deploy Authorization** check in GitHub ("Awaiting authorization from a project member") until a project member approves it in the dashboard. Pushes from people with write access skip this step.

We tested this with a pull request on a private test repository. Unkey built the preview from the PR's branch, created a GitHub Deployment for it, and posted the comment below on the PR.

Give the preview environment its own values, like a test database, test-mode payment keys, and maybe a separate keyspace so preview keys can't call production.

I created a preview by hand to see what happens to it over its lifetime. It got its own domains, and `availableActions` lists what you can do with it.

![Terminal: preview deployment created, serving, stopped (503 deployment_offline) and woken again](/images/blog-images/deploy-api-previews-rollback-monitoring/02-preview.png)

Previews clean up after themselves, and the docs list when each one stops automatically.

| Trigger                                                           | What stops                                    | When              |
| ----------------------------------------------------------------- | --------------------------------------------- | ----------------- |
| New preview deployment on the same branch                         | The deployment that was on that branch domain | 1 minute later    |
| Preview deployment gets no requests                               | That deployment                               | After 1 hour idle |
| You stop it (**Stop deployment** or `deployments.stopDeployment`) | That deployment                               | Right away        |

A stopped preview answers `503` with `err:frontline:capacity:deployment_offline`, and you wake it with **Wake deployment** or `deployments.startDeployment`. Mine reported `ready` about three seconds after the start call, and the preview domain returned `200` about eight seconds after that. That comes from a single measurement, so don't treat it as a guarantee. The first request after stopping also got a `504 request_timeout` before the documented `503` showed up.

## Step 3: Require an API key and add a rate limit at the gateway

Every Compute app sits behind our gateway, and that's where policies run. You start by getting a keyspace and a key from API Management.

```
$ unkey api apis create-api --name=blog-draft-payments --output json
{
  "meta": { "requestId": "req_xe4rFydPq" },
  "data": { "apiId": "api_HIZ9nP2KX" }
}
```

Next, create a key for a customer. `externalId` links it to an identity, so all of that customer's keys count as the same subject.

```
$ curl -s -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{"apiId":"api_HIZ9nP2KX","prefix":"pay","externalId":"blog-draft-acme","name":"blog-draft acme laptop","meta":{"plan":"pro"}}'
{"data":{"key":"pay_QgsM...****","keyId":"key_Kpa8xHhc1"},"meta":{"requestId":"req_fTtBDYns4"}}
```

This is the only time you get the full key, because we only store a hash. Hand it to the customer now.

Be careful with IDs here. The gateway needs the **keyspace ID** (`ks_...`), and if you pass the API ID (`api_...`) instead, the call fails.

```
{"error":{"detail":"Keyspace \"api_HIZ9nP2KX\" does not exist.","status":404,"title":"Not Found","type":"https://unkey.com/docs/errors/unkey/data/key_space_not_found"}, ...}
```

You'll find both IDs on the keyspace's **Settings** page, and from the API, `keys.verifyKey` returns the keyspace ID as `keyspaceId`.

```
{"data":{"code":"VALID","enabled":true,"identity":{"externalId":"blog-draft-acme","id":"id_niCA4IOmB"},"keyId":"key_Kpa8xHhc1","keyspaceId":"ks_tllKF8lmh","meta":{"plan":"pro"},"name":"blog-draft acme laptop","valid":true}, ...}
```

Now set the policies for production. They run from top to bottom, and a per-caller rate limit has to come after the key check, or every request counts as `unknown`. I used 5 requests per minute so it's easy to hit. In production you'd set something more like 100.

```
$ curl -s -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "blog-draft-payments",
    "app": "api",
    "environment": "production",
    "policies": [
      { "name": "Require a key", "enabled": true,
        "keyauth": { "keyspaces": ["ks_tllKF8lmh"] } },
      { "name": "5 per minute per caller", "enabled": true,
        "ratelimit": { "limit": 5, "windowMs": 60000,
                       "identifiers": [{ "authenticatedSubject": {} }] } }
    ]
  }' | jq
{
  "data": {},
  "meta": { "requestId": "req_JvarCEnO2" }
}
```

The root key needs `environment.*.set_policies`. In the dashboard you add them with **Policies > Add Policy > Key Auth** and then **Rate Limit**.

**Policies only apply to the next deployment.** A deployment keeps the image, variables and policies it was created with, so after I saved, the live one still answered requests that had no key.

```
$ curl -s -o /dev/null -w "%{http_code}\n" https://blog-draft-payments-api-grok-bot.unkey.app/v1/hello
200
```

You need to redeploy, either with **Redeploy** in the dashboard or from the existing deployment.

```
$ unkey api deployments create-deployment --project=blog-draft-payments --app=api \
    --environment=production --deployment='{"deploymentId":"d_GjCkWjVim"}' --output json
{
  "meta": { "requestId": "req_fMCrhFQlt" },
  "data": { "deploymentId": "d_oeD1HeGSE" }
}
```

Once the new deployment is live, a request with no key gets `401 missing_credentials`, a wrong key gets `401 invalid_key`, and the sixth request in the window gets `429` with `Retry-After`. Every limited route also sends back `X-RateLimit-*` headers.

![Terminal: 401 without a key, 401 with a bad key, then 200s counting down to a 429 with Retry-After](/images/blog-images/deploy-api-previews-rollback-monitoring/03-key-auth-ratelimit.png)

Rejected requests never reach your code. Requests that pass arrive with an `X-Unkey-Principal` header describing the caller, so your app never has to call Unkey itself.

![Terminal: the X-Unkey-Principal JSON the app received for a verified key](/images/blog-images/deploy-api-previews-rollback-monitoring/04-principal.png)

`subject` is the identity's `externalId`, or the key ID if the key has no identity. `authenticatedSubject` counts requests by that value, so all of a customer's keys share the same rate limit. The gateway strips any `X-Unkey-*` header a client sends, and Compute deployments can only be reached through the gateway, so you can trust the header inside Compute. Anywhere else, someone can forge it.

Preview has its own list of policies. I only set production's, so my preview stayed open to anyone. If your previews shouldn't be public, set policies for them too, or use **All Environments** in the dashboard.

## Step 4: Watch requests, logs and metrics

You don't install anything, and Unkey records all of the following for you.

- **Request logs** have one row per request that reached your app, with method, host, path, status, region, deployment, instance, and latency split into `gateway_latency` and `instance_latency`. You'll find them under **Requests**.
- **Runtime logs** are stdout and stderr from every instance, with the severity parsed out, under **Logs**.
- **Metrics** cover requests per second, latency percentiles, CPU, memory, disk and network per deployment, and a **Network** view shows regions and instances.
- **Build logs** show each build step and its output.

![The project Requests view filtered to the api app with one request's deployment details open](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-requests.png)

![The deployment Network view with instances in four regions](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-network.png)

![RPS, latency, CPU and memory charts under the deployment's network map](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-metrics.png)

If you plan to alert on the request log, know that **requests rejected by a policy aren't in it**. The 401s and 429s above never reached the app. Gateway key checks do show up in API Management's verification analytics, next to your own `keys.verifyKey` calls.

You can query the request log with SQL through the analytics API, using `gateway_requests_v1`. This example from the docs finds the paths with the most 5xx responses in the last 24 hours.

```bash
# UNVERIFIED: returned 412 analytics_not_configured in the test workspace (see below)
curl -X POST https://api.unkey.com/v2/analytics.getGatewayRequests \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"SELECT path, count() AS total FROM gateway_requests_v1 WHERE response_status >= 500 AND time >= toUnixTimestamp64Milli(now64(3) - INTERVAL 24 HOUR) GROUP BY path ORDER BY total DESC LIMIT 10"}'
```

The root key needs the wildcard `project.*.read_gateway_requests`, because a permission for a single project won't work. Queries can reach back 3 days on Starter, 7 on Pro and 14 on Business, but rows are only kept for 7 days, so you get whichever is shorter. Runtime logs live in `runtime_logs_v1`, and you read them with `analytics.getRuntimeLogs`.

When I called the analytics API I got `412` with `err:unkey:data:analytics_not_configured`, even though the Requests, Network and metrics views in the dashboard all worked. The docs say there's no dashboard setting for API access, so you have to ask support to turn it on.

If you want to keep logs longer or use your own tools, a log drain forwards one stream (gateway HTTP requests, runtime logs, key verifications, rate limits or audit logs) to an HTTPS endpoint or an Axiom dataset. Every plan starts with a log drain limit of 0, so you'll need to ask support to raise it.

## Step 5: Roll back a bad deploy

Say the release you just shipped is bad. Start by listing production deployments, where `availableActions` shows which ones you can roll back to.

```
$ unkey api deployments list-deployments --project=blog-draft-payments --app=api --environment=production --output json \
  | jq -r ".data[] | [.id, .status, (.isCurrent|tostring), (.availableActions|join(\",\"))] | @tsv"
d_bZ03J0OgK	ready	true
d_oeD1HeGSE	ready	false	promote,rollback
d_GjCkWjVim	ready	false	promote,rollback
```

You can roll back with **Rollback** in the dashboard, with `POST /v2/deployments.rollbackDeployment` and `{"deploymentId":"d_..."}`, or with the CLI. The root key needs `environment.*.rollback_deployment`. I used the CLI, with a loop hitting production every half second so you can see which deployment answered.

![Terminal: CLI rollback with a poller showing the live domain switch from d_bZ03J0OgK to d_oeD1HeGSE](/images/blog-images/deploy-api-previews-rollback-monitoring/05-rollback.png)

The command returns as soon as the rollback is accepted. The target served its first request about 4.3 seconds later, and a second rollback switched over in about 4.4 seconds. That was two runs from one laptop in one region, so don't read it as a benchmark.

![The Instant rollback dialog showing the current deployment and the previous deployment it will switch to](/images/blog-images/deploy-api-previews-rollback-monitoring/deploy-rollback-dialog.png)

There are limits on which deployments you can roll back to.

- The target must be a `ready` production deployment that isn't stopped and isn't the live one.
- When a live deployment gets replaced, it stays up as a standby for 30 minutes and then stops, and a stopped deployment can't be a target. To get back to one, **Redeploy** it, wait for `ready`, and promote it, or roll forward with a fixed commit instead.
- You can't stop or start production deployments by hand, since stopping the live one would take the app offline.

## What happens to traffic during a rollback

Nothing restarts during a rollback. The target is already running, so the domains (live, environment and any verified custom domains) move to it in one step. The old deployment keeps serving until the move reaches every region, which the docs say happens "within a few seconds". In the poller that was roughly the first three seconds. Normal deploys overlap in the same way, and after a new deployment reported `ready`, the first request still went to the previous one.

The target keeps the policies it was created with, so if you've changed key auth or rate limits since then, those roll back too.

## Getting back to normal after a rollback

After a rollback, the app is marked as rolled back.

```
$ unkey api apps get-app --project=blog-draft-payments --app=api --output json | jq ".data | {slug, isRolledBack}"
{
  "slug": "api",
  "isRolledBack": true
}
```

According to the docs, while the app is rolled back, new production deployments still build and reach `ready`, but they don't go live. That way a push in the middle of an incident can't undo your rollback. To end it, you can promote the deployment you rolled back to, which is called a "confirm rollback". Traffic stays where it is, and new pushes start going live again. You can also promote a newer deployment that has the fix, using **Promote** or `deployments.promoteDeployment`. The deployment it replaces stops after 30 minutes.

## How this compares with GitHub Actions plus Cloud Run, ECS or Kubernetes

None of these pieces is hard on its own, but with the other setups you own more of them. The rows link to each provider's docs.

| Step                                 | Unkey                                                                        | GitHub Actions + Cloud Run                                                                                                                                 | GitHub Actions + ECS                                                                                                                                             | GitHub Actions + Kubernetes                                                                                                                                                  |
| ------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploy on push                       | Connect the repo; built-in                                                   | Workflow runs `gcloud run deploy`                                                                                                                          | Workflow registers a task definition and updates the service                                                                                                     | Workflow applies manifests or sets the image                                                                                                                                 |
| Preview per branch or PR             | Built-in, with a branch domain and fork approval                             | Workflow deploys a revision with `--no-traffic --tag` to get a tagged URL ([docs](https://cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)) | Not covered in the linked docs; you script a service per PR                                                                                                      | Not covered in the linked docs; you script a namespace or release per PR                                                                                                     |
| Clean up previews                    | Auto-stop after 1 hour idle, or 1 minute after a newer preview on the branch | You remove tags or revisions yourself                                                                                                                      | Your workflow tears down what it created                                                                                                                         | Your workflow tears down what it created                                                                                                                                     |
| Roll back                            | `rollback-deployment` or the **Rollback** button                             | `gcloud run services update-traffic SERVICE --to-revisions REVISION=100` ([docs](https://cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration))  | Blue/green deployments let you revert to the blue revision ([docs](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-blue-green.html)) | `kubectl rollout undo deployment/NAME`, optionally `--to-revision` ([docs](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-back-a-deployment)) |
| API key auth and per-key rate limits | Gateway policies backed by API Management keys                               | A separate gateway or code in your app                                                                                                                     | A separate gateway or code in your app                                                                                                                           | An ingress or gateway add-on, or code in your app                                                                                                                            |
| Request logs                         | Built-in, plus SQL via the analytics API                                     | Cloud Logging                                                                                                                                              | CloudWatch, if you configure it                                                                                                                                  | Whatever logging stack you run                                                                                                                                               |

Render's [service previews](https://render.com/docs/service-previews) are the closest built-in match. You choose **Manual** or **Automatic** PR previews, and Render deletes a preview when its PR is merged or closed. If previews are all you need, Render is a fine choice. Unkey also puts a gateway in front of production and previews, and gives you rollback and request logs you can query, all in one product.

Once you're past the included credit, you pay for the vCPU and memory you actually use on average, as opposed to the ceiling you configured. You also pay for allocated ephemeral disk, egress, and active keys verified through a Compute key auth policy. The rates are $0.000006944 per vCPU-second, $0.000003472 per GB-second of memory, $0.00000006 per GB-second of disk, $0.05 per GB of egress, and $0.002 per active key per month. To give you a sense of scale, the default instance (0.25 vCPU, 256 MiB) running flat out for a 30-day month comes to about $4.50 of CPU and $2.25 of memory at those rates, before the included credit. An idle API costs less than that.

If you want a hard cap on the bill, set a monthly budget under **Settings > Billing**. Admins get an email at 50, 75 and 100 percent of it. If you turn on **Stop workloads at the budget**, every deployment stops at 100 percent, and the gateway answers `402 spend_limit_reached` until you raise or remove the budget or the next month starts. Nothing gets deleted, and your deployments come back without a redeploy.
