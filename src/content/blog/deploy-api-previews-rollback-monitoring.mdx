# Deploy an API with preview environments and request logs

A public API needs a place to run, a preview for each pull request, a check on who is calling, and logs when something breaks. This post does that on Unkey by connecting a GitHub repository. Pushes deploy the app. Compute runs it, API Management issues and checks keys, and Unkey records each request the app serves.

## What you'll have at the end

You get a production URL on `unkey.app` that updates when you push to your default branch, and a preview URL for every other branch and fork pull request. The gateway checks API keys and rate limits each caller. Logs and metrics show up without an SDK.

You need a Compute plan before the first deploy. The dashboard asks you to **Choose a Compute plan**. Only a workspace admin can pick one.

## The sample API

Any language works if the process listens on `PORT`. Unkey sets that to the configured port, 8080 by default. This is a small Hono app.

{/* prettier-ignore */}
```js
// index.js
import { Hono } from "hono";
import { serve } from "@hono/node-server";

const app = new Hono();

app.get("/healthz", (c) => c.text("ok"));

app.get("/v1/hello", (c) => {
  // Set by the gateway after a key-auth policy verifies the caller.
  const raw = c.req.header("x-unkey-principal");
  const principal = raw ? JSON.parse(raw) : null;
  return c.json({
    hello: principal?.subject ?? "anonymous",
    deployment: process.env.UNKEY_DEPLOYMENT_ID ?? "local",
  });
});

const port = Number(process.env.PORT ?? 8080);
serve({ fetch: app.fetch, port });
console.log(`listening on ${port}`);
```

Locally, with and without a principal header:

```
$ curl -s localhost:8080/v1/hello
{"hello":"anonymous","deployment":"local"}
$ curl -s localhost:8080/v1/hello -H 'X-Unkey-Principal: {"version":"v1","subject":"acme","type":"API_KEY","source":{"key":{"keyId":"key_123","keySpaceId":"ks_123","meta":{}}}}'
{"hello":"acme","deployment":"local"}
```

Unkey sets `UNKEY_DEPLOYMENT_ID` on every instance, so a response can name which deployment answered.

## Step 1: Connect the repository and deploy

### From the dashboard

1. Open **Projects** and choose **Create project**, then enter a **Project Name**. The **Slug** is generated from the name. That slug is what the API and CLI use. The new project opens on an empty Apps list.

![The Create New Project dialog with a project name and slug](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-create-project.png)

2. Choose **Create app**. The wizard opens on **Deploy a new app** and asks where the code comes from. Choose **GitHub repository**. This step has no name or slug fields. The first time you do this in a workspace, GitHub asks you to install the Unkey GitHub App and grant it repository access.

![Deploy a new app, with GitHub repository as the source](/images/blog-images/deploy-api-previews-rollback-monitoring/deploy-create-app.png)

Then pick the repository and branch.

![The Select a repository step listing GitHub repositories with a branch picker for each](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-repo-picker.png)

3. Open **App settings > Environments**. Production and preview each show compute, domains, which branch they follow, and auto-deploy. In this app both environments run one instance at 1/4 vCPU and 256 MiB in Oregon, Singapore, Frankfurt, and N. Virginia. Production follows `main`. Preview follows every other branch, and each branch gets its own URL. Auto-deploy is on for both.

![Production environment settings: four regions, the live and production domains, branch main, and auto-deploy on](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-configure.png)

![Preview environment settings: the same four regions, the preview domain, all unassigned branches, and auto-deploy on](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-configure-2.png)

4. Root directory, Dockerfile, and watch paths live on the build settings screen, not on Environments. Point the root at a subdirectory for a monorepo, and add a watch path such as `services/api/**` when pushes that miss that path should be recorded as `skipped`. Environment variables are scoped per environment. Mark secrets sensitive and they stay write-only.

5. Choose **Deploy**. The deployment moves through `pending`, `starting`, `building`, `deploying`, `network` (shown as **Assigning Domains**), and `finalizing` until it is `ready`. The build log streams during `building`.

![A GitHub deployment while it is still deploying, with the build log open](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-building.png)

The deployment page shows the branch and commit it came from. Unkey builds that commit from the repository.

![The same deployment at Ready, with its domains and one instance in each of four regions](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-ready.png)

A new app starts at port 8080 with 0.25 vCPU and 256 MiB. This one is running in the four regions from the environment settings, one instance in each.

### From the API or CLI

Every call is a `POST` to `https://api.unkey.com/v2/{service}.{procedure}` with a root key in `Authorization: Bearer`.

`projects.createProject` creates the project. `apps.createApp` connects the repo when the body includes `"git":{"repository":"owner/repo"}`. Unkey fills in `defaultBranch` from the repository.

```bash
curl -X POST https://api.unkey.com/v2/deployments.createDeployment \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{"project":"my-project","app":"api","environment":"production","git":{"branch":"main"}}'
```

That returns `201` and a deployment id. Poll `deployments.getDeployment`. On a small app the status moves through `building` and `deploying` to `ready` in about 30 seconds. The app is then live at `https://<project>-<app>-<workspace>.unkey.app`.

`POST /v2/deployments.createDeployment` is deprecated in favor of `POST /v3/deployments.createDeployment`. On v3, `oci.image` replaces `image.dockerImage`.

![getDeployment for a production deployment built from the main branch, status ready, with its unkey.app domains](/images/blog-images/deploy-api-previews-rollback-monitoring/01-deploy-ready.png)

A ready deployment lists the git branch, the commit, and the domains: the live domain, an environment domain, a branch domain, a commit domain, and one pinned to that deployment.

Install the CLI with `npm install -g unkey` and export `UNKEY_ROOT_KEY`. The same four calls are `unkey api projects create-project`, `unkey api apps create-app --git='{"repository":"owner/repo"}'`, `unkey api deployments create-deployment --git='{"branch":"main"}'`, and `unkey api deployments get-deployment`.

If the image is already in a registry, `unkey deploy docker.io/traefik/whoami:v1.10.3 --project=my-project --app=api --env=production` deploys it. That image listens on port 80, so set the app port first with `unkey api apps update-settings --port=80`. The command prints `Deployment completed successfully` and finishes in about 9 seconds.

A workspace builds one deployment at a time. The rest wait in `pending`. Production jumps ahead of preview, so a fix does not wait on pull request builds. A deployment that has waited an hour fails. Deploy it again once the queue has drained.

## Step 2: Every branch and pull request gets a preview

Once the repository is connected, a push to the default branch deploys production. A push to any other branch creates a preview with its own branch domain. Each one shows up in GitHub as a deployment, and Unkey keeps a single pull request comment updated with a **Visit Preview** link.

![The app's Deployments list with a preview deployment above the production deployment](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-preview-list.png)

Open a preview deployment to see its branch, commit, environment, and domains.

![A preview deployment page with its branch, commit, Preview environment, and domains](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-preview-detail.png)

A fork pull request is different. Its code would run with your preview variables, including database URLs and third-party keys. It waits in `awaiting_approval` until a project member approves it in the dashboard. GitHub shows a failing **Unkey Deploy Authorization** check ("Awaiting authorization from a project member") while it waits. Pushes from people with write access skip that check.

Give the preview environment its own values: a test database, test-mode payment keys, maybe a separate keyspace so preview keys cannot call production.

Previews stop on their own.

| Trigger                                                           | What stops                                    | When              |
| ----------------------------------------------------------------- | --------------------------------------------- | ----------------- |
| New preview deployment on the same branch                         | The deployment that was on that branch domain | 1 minute later    |
| Preview deployment gets no requests                               | That deployment                               | After 1 hour idle |
| You stop it (**Stop deployment** or `deployments.stopDeployment`) | That deployment                               | Right away        |

A stopped preview answers `503` with `err:frontline:capacity:deployment_offline`. Wake it with **Wake deployment** or `deployments.startDeployment`. It goes through `deploying` and back to `ready`. You cannot start one while the workspace is suspended by its Compute spend budget.

![Stopping a preview deployment, the branch domain returning 503 deployment_offline, then a 200 after it is started again](/images/blog-images/deploy-api-previews-rollback-monitoring/02-preview.png)

## Step 3: Require an API key and add a rate limit at the gateway

Every Compute app sits behind the gateway. Policies run there, before the request reaches your code. Start with a keyspace and a key from API Management. The API calls a keyspace an API.

```bash
curl -X POST https://api.unkey.com/v2/apis.createApi \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "my-api" }'
```

The response includes `apiId`. Save it. You need it whenever you create a key.

Create a key for a customer. `externalId` links the key to an identity, so that customer's keys count as one subject.

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"apiId":"api_...","prefix":"pay","externalId":"acme","name":"acme laptop","meta":{"plan":"pro"}}'
```

`data.key` is the full key, and this response is the only time you get it. Unkey stores a hash. Hand the key to the customer now.

The gateway wants the keyspace id (`ks_...`). If you pass the API id (`api_...`) instead, the call returns 404 and says the keyspace does not exist. Both ids are on the keyspace **Settings** page. `keys.verifyKey` returns the keyspace id as `keyspaceId`.

Set the production policies next. They run from top to bottom. Put the rate limit after the key check, or every request is counted as `unknown`. Five a minute is enough to see it trip. In production, start nearer 100. The root key needs `environment.*.set_policies`. In the dashboard, use **Policies > Add Policy > Key Auth**, then **Rate Limit**.

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "blog-draft-gh",
    "app": "blog-draft-gh",
    "environment": "production",
    "policies": [
      { "name": "Require a key", "enabled": true,
        "keyauth": { "keyspaces": ["ks_..."] } },
      { "name": "5 per minute per caller", "enabled": true,
        "ratelimit": { "limit": 5, "windowMs": 60000,
                       "identifiers": [{ "authenticatedSubject": {} }] } }
    ]
  }'
```

A deployment keeps the image, variables, and policies it was created with. Saving a policy does nothing to the one that is already live. Redeploy from the deployment page. The new policies then take a moment to reach every domain.

With the new deployment live, a request with no key gets `401` `missing_credentials`. A bad key gets `401` `invalid_key`. Past the limit, the caller gets `429` `rate_limited` and `Retry-After`. Responses also include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` in Unix seconds.

![Calls to the production domain: 401 with no key, 401 with a bad key, then 404s while the rate limit counts down, and 429 on the sixth request](/images/blog-images/deploy-api-previews-rollback-monitoring/03-key-auth-ratelimit.png)

The `404` body is `page not found` from the demo app. It has no `/` route. The gateway had already accepted the key, which is why the rate limit headers still move. The sixth request is `429`.

A rejected request never reaches your code. A request that passes arrives with an `X-Unkey-Principal` header, so the app does not call Unkey itself. On the demo app, `/whoami` returns that header.

```js
app.get('/whoami', (c) => {
  const raw = c.req.header('x-unkey-principal');
  return c.json({ principal: raw ? JSON.parse(raw) : null });
});
```

![/whoami on a preview deployment, returning the X-Unkey-Principal JSON for a verified key](/images/blog-images/deploy-api-previews-rollback-monitoring/04-principal.png)

`subject` is the identity's `externalId`, or the key id when the key has no identity. `authenticatedSubject` counts by that value, so one customer's keys share a limit. The gateway strips any `X-Unkey-*` header the client sends. Compute deployments are only reachable through the gateway, so the header inside Compute is the one Unkey set. Run the same code somewhere else and a caller can forge it.

Preview has its own policy list. If a preview should not be public, set policies for it too, or choose **All Environments** in the dashboard.

## Step 4: Watch requests, logs and metrics

Nothing to install. Unkey records the traffic for you.

Request logs have one row per request that reached your app: method, host, path, status, region, deployment, instance, and latency split into `gateway_latency` and `instance_latency`. Open **Requests**.

![The project Requests view filtered to one app, with a request's deployment details open](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-requests.png)

Runtime logs are stdout and stderr from every instance, with the severity parsed out. They live under **Logs**.

The deployment page charts requests per second, latency, CPU, and memory. The docs also list disk, network, instance count, and instance events. The **Network** view draws the regions and instances.

![The deployment Network view with one instance in each of four regions](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-network.png)

![RPS, latency, CPU, and memory charts under the network map](/images/blog-images/deploy-api-previews-rollback-monitoring/gh-metrics.png)

Build logs are the steps and output from the image build, on the deployment page while it is building.

A policy rejection never reaches the app, so it is missing from the request log. The key check still shows up in API Management's verification analytics, next to your own `keys.verifyKey` calls.

`analytics.getGatewayRequests` runs SQL against `gateway_requests_v1`. The root key needs the wildcard `project.*.read_gateway_requests`.

```bash
curl -X POST https://api.unkey.com/v2/analytics.getGatewayRequests \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"SELECT path, count() AS requests, avg(total_latency) AS avg_latency FROM gateway_requests_v1 WHERE time >= toUnixTimestamp64Milli(now64(3) - INTERVAL 1 HOUR) GROUP BY path ORDER BY requests DESC LIMIT 10"}'
```

A query that hits data returns `200`. Rows show up about 20 seconds after the traffic. The body is one object per path, with the count and the latency:

```json
{
  "data": [{ "path": "/healthz", "requests": "<count>", "avg_latency": "<ms>" }]
}
```

Queries only cover the last 7 days. Ask for anything older and the API returns `400` `query_range_exceeds_retention`.

Runtime logs are a different call, `analytics.getRuntimeLogs` on `runtime_logs_v1`. The root key needs its own runtime-logs read permission, `project.*.read_runtime_logs`. The gateway-requests permission does not cover them.

To keep logs longer, or to use your own tools, a log drain forwards one stream (gateway HTTP requests, runtime logs, key verifications, rate limits, or audit logs) to an HTTPS endpoint or an Axiom dataset. Every plan starts with a log drain limit of 0. Ask support to raise it.

## How this compares with GitHub Actions plus Cloud Run, ECS or Kubernetes

The other setups leave more of this to you. Each row links to that provider's docs.

| Step                                 | Unkey                                                                        | GitHub Actions + Cloud Run                                                                                                                                 | GitHub Actions + ECS                                         | GitHub Actions + Kubernetes                                              |
| ------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Deploy on push                       | Connect the repo; built-in                                                   | Workflow runs `gcloud run deploy`                                                                                                                          | Workflow registers a task definition and updates the service | Workflow applies manifests or sets the image                             |
| Preview per branch or PR             | Built-in, with a branch domain and fork approval                             | Workflow deploys a revision with `--no-traffic --tag` to get a tagged URL ([docs](https://cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)) | Not covered in the linked docs; you script a service per PR  | Not covered in the linked docs; you script a namespace or release per PR |
| Clean up previews                    | Auto-stop after 1 hour idle, or 1 minute after a newer preview on the branch | You remove tags or revisions yourself                                                                                                                      | Your workflow tears down what it created                     | Your workflow tears down what it created                                 |
| API key auth and per-key rate limits | Gateway policies backed by API Management keys                               | A separate gateway or code in your app                                                                                                                     | A separate gateway or code in your app                       | An ingress or gateway add-on, or code in your app                        |
| Request logs                         | Built-in, plus SQL via the analytics API                                     | Cloud Logging                                                                                                                                              | CloudWatch, if you configure it                              | Whatever logging stack you run                                           |

Render's [service previews](https://render.com/docs/service-previews) are the closest built-in match for the preview row. You choose **Manual** or **Automatic** pull request previews, and Render deletes a preview when its pull request is merged or closed. Unkey also puts a gateway in front of production and previews, and the request log is queryable.

## Cost

API Management and Compute are billed separately. You can use either one without the other. Prices below are from [unkey.com/pricing](https://www.unkey.com/pricing).

API Management's Free tier includes 150,000 valid requests a month, 1,000 API keys, and 1 day of log retention. Invalid requests, including rate-limited calls and bad keys, do not count toward that quota. Audit logs on Free are kept for 3 days.

Compute has three plans. Each one includes a monthly usage credit equal to the fee. Until December 31, 2026, the first month is discounted: Starter is $0 then $5, Pro is $20 then $25, and Business is $45 then $50. On Starter, credit left over from that first month carries to the next bill. Unused credits otherwise do not roll over.

|                         | Starter       | Pro           | Business        |
| ----------------------- | ------------- | ------------- | --------------- |
| Monthly fee             | $5            | $25           | $50             |
| First month             | $0            | $20           | $45             |
| Usage credit each month | $5            | $25           | $50             |
| Max per instance        | 2 vCPU, 2 GiB | 8 vCPU, 8 GiB | 16 vCPU, 32 GiB |
| Instances per region    | 4             | 8             | 16              |
| Custom domains          | 1             | Unlimited     | Unlimited       |
| Log retention           | 3 days        | 7 days        | 14 days         |
| Team members            | None          | Unlimited     | Unlimited       |

Every plan allows one concurrent build, git push to deploy, and a preview for each pull request. Preview usage is billed at the same rates as production.

Past the included credit, you pay for average actual vCPU and memory use, allocated disk, egress, and active keys verified through a Compute key auth policy. CPU time counts while your code is executing. Memory is the average the instance uses. The rates on the pricing page are per second. A 30-day month is 2,592,000 seconds, so the same rates in larger units are:

| Meter       | Rate                   |
| ----------- | ---------------------- |
| vCPU        | $0.0249984 per hour    |
| Memory      | $8.999424 per GB-month |
| Disk        | $0.15552 per GB-month  |
| Egress      | $0.05 per GB           |
| Active keys | $2 per 1,000 per month |

The default instance is 0.25 vCPU and 256 MiB (0.25 GB). Flat out for those 2,592,000 seconds, CPU is `0.25 × 0.000006944 × 2592000 = $4.499712`. Memory is `0.25 × 0.000003472 × 2592000 = $2.249856`. That is $6.749568 before the included credit. An idle instance pays less CPU, because idle time waiting on I/O is not billed.

A monthly budget caps the bill.

- Set it in whole dollars under **Settings > Billing**. Only a workspace admin can change it.
- Admins get an email the first time month-to-date spend crosses 50, 75, and 100 percent.
- **Stop workloads at the budget** is off until you turn it on. At 100 percent, running deployments stop and every request gets `402` `spend_limit_reached`.
- Remove the budget, turn the stop option off, or wait for the next month, and the live deployment comes back without a redeploy. Raising the budget resumes compute once spend has stayed under the new budget for two checks in a row.
- Nothing is deleted.
