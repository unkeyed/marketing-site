# How to add API key authentication to your API without building a key system

You have an API, and your customers need keys to call it. This post is about issuing keys for **your own** API. A lot of "API key" search results describe a different job, using a key to call someone else's service like Google Cloud or OpenAI, and we don't cover that here.

Everything below ran against a real Unkey workspace on 2026-10-13 using `@unkey/api` 2.5.1 and `@unkey/hono` 2.0.0. The terminal output is copied from those runs, with keys redacted. The developer portal is marked UNVERIFIED because we could not run it for this draft. Parts of the gateway section that we did not test are marked the same way.

## What a key system has to do

If you build API keys yourself, you're signing up to build and run everything in the list below.

- **Generate** keys with enough entropy, and give them a readable prefix so people can tell `sk_live` from `sk_test` in logs.
- **Hash** them before you store them, and never keep or log the plaintext.
- **Store** the hash with an owner, metadata, expiry and an enabled flag.
- **Verify** them quickly on every request, and report why a key failed.
- **Rotate** them with an overlap window, so customers can deploy the new key before the old one stops working.
- **Revoke** a key the moment it leaks.
- **Rate limit** each key, so one customer's runaway script doesn't take everyone else down.
- **Record usage** per key and per customer.
- **Let customers manage** their own keys without filing a support ticket.

[API key management vs. an API gateway](https://www.unkey.com/blog/api-key-management-vs-gateway) goes into why each item matters. Below we work through every item with Unkey's API Management product from inside an existing app, and then do it all again with no code for apps that run on Unkey Compute.

## Step 1: Create a keyspace and a root key

Your backend talks to Unkey with a root key. Create one in the dashboard under **Settings > Root Keys** with `api.*.create_api`, `api.*.create_key` and `api.*.verify_key`, then store it as `UNKEY_ROOT_KEY` on your server. A root key should never end up in a browser or a mobile app.

![The New Root Key dialog in Settings with Keyspaces Write, Keys Write and Keys Verify selected](/images/blog-images/api-key-authentication/auth-root-key-dialog.png)

A keyspace holds the keys for one product or environment, though the API and older dashboard copy call it an API. You can create one in the dashboard under **Keyspaces (APIs)** or with a single call.

```bash
curl -X POST https://api.unkey.com/v2/apis.createApi \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{ "name": "blog-draft-keyauth" }'
```

```json
{"data":{"apiId":"api_7HF4gFZpu"},"meta":{"requestId":"req_hVdmCjIrs"}}
```

Hold on to the `apiId`, because you need it every time you create a key.

## Step 2: Issue a key when a customer signs up

Start by installing the SDKs.

```bash
npm install hono @unkey/hono @unkey/api
```

Your backend creates the key when a user signs up or clicks "new key".

```ts
import { Unkey } from "@unkey/api";

const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? "" });

const created = await unkey.keys.createKey({
  apiId: process.env.UNKEY_API_ID ?? "",
  prefix: "sk_live",
  externalId: "user_123",
  meta: { plan: "free" },
  permissions: ["items.read"],
  ratelimits: [{ name: "requests", limit: 5, duration: 60000, autoApply: true }],
});
// show created.data.key to the user once; store created.data.keyId
```

```json
{
  "meta": { "requestId": "req_s9FLcJXld" },
  "data": {
    "keyId": "key_jSF1UzeET",
    "key": "sk_live_YVpp…████"
  }
}
```

A quick note on each field in that call.

- `prefix` gives you keys that start with `sk_live_…`. Anyone who can see the key can see the prefix, so keep customer names and secrets out of it.
- `externalId` is your own user or org ID. Unkey creates an identity for it and sends it back on every verification, so your handler knows who is calling without looking anything up in your database.
- `meta` comes back on every verification too, so keep it small and leave secrets out of it.
- `permissions` get created in the workspace if they don't exist yet. We checked by creating `items.read` by hand afterwards, and got a 409 because the call above had already made it.
- `ratelimits` puts a limit on this key. We used 5 per minute only so you can watch it trip in Step 3. `autoApply` is required, and the call fails with a 400 if you leave it out.

The plaintext key is in `created.data.key`, and you only get to see it this once. According to the docs, "Unkey keeps only a hash, plus an encrypted copy if you asked for a recoverable key." DIY guides spend most of their length on hashing, the storage schema and constant-time comparison, and you don't have to write any of that. Show the key to the user, store the `keyId`, and keep the response out of your logs.

## Step 3: Check the key on every request

### With Hono middleware

`@unkey/hono` reads the bearer token, calls `keys.verifyKey` and puts the result in context. This is the full server we ran on Node.

```ts
import { serve } from "@hono/node-server";
import { Hono } from "hono";
import { HTTPException } from "hono/http-exception";
import { type UnkeyContext, unkey } from "@unkey/hono";

const app = new Hono<{ Variables: { unkey: UnkeyContext } }>();

function statusFor(code: string): 401 | 402 | 403 | 429 {
  switch (code) {
    case "RATE_LIMITED":
      return 429;
    case "USAGE_EXCEEDED":
      return 402;
    case "FORBIDDEN":
    case "INSUFFICIENT_PERMISSIONS":
      return 403;
    default:
      return 401;
  }
}

app.use(
  "/items/*",
  unkey({
    rootKey: process.env.UNKEY_ROOT_KEY ?? "",
    permissions: "items.read",
    handleInvalidKey: (c, result) =>
      c.json({ error: result.data.code }, statusFor(result.data.code)),
    onError: (c, err) => {
      console.error("unkey", err.message);
      return c.json({ error: "authentication unavailable" }, 503);
    },
  }),
);

app.get("/items/list", (c) => {
  const { data } = c.get("unkey");
  return c.json({
    items: [],
    owner: data.identity?.externalId,
    plan: data.meta?.plan,
    remaining: data.ratelimits?.[0]?.remaining,
  });
});

app.onError((err, c) => {
  console.error(err);
  if (err instanceof HTTPException) return c.json({ error: "authentication unavailable" }, 503);
  return c.json({ error: "internal error" }, 500);
});

serve({ fetch: app.fetch, port: 3000 });
```

We called it with no key, then a valid key, then a made-up key, and then sent enough requests to hit the 5-per-minute limit.

![curl against the Hono server: 401 with no key, 200 with a valid key, 401 NOT_FOUND for an unknown key, then 429 RATE_LIMITED on the sixth request](/images/blog-images/api-key-authentication/01-hono-curl-401-200-429.png)

On the valid request, the handler already knows who's calling (`"owner":"user_123"`) and what plan they're on (`"plan":"free"`) without touching the database.

That code has a few spots that are easy to get wrong.

**Always set `handleInvalidKey`.** The middleware only stops a request by itself when the key is *missing*. When a key fails verification, it calls `handleInvalidKey` if you gave it one. If you didn't, it stores the failed result and calls `next()`. We ran the middleware without it and sent a made-up key.

![Without handleInvalidKey, an unknown key gets HTTP 200 and a body of items secret with valid false](/images/blog-images/api-key-authentication/04-hono-without-handleinvalidkey.png)

That run used a small route on port 3002 that printed the check. The response was HTTP 200 and `{"items":["secret"],"valid":false}`. The handler printed above returns `items: []` and does not echo `valid`. You need to either set `handleInvalidKey` or check `c.get("unkey").data.valid` in every handler.

**`onError` doesn't catch everything.** According to the Hono guide, it only runs for unexpected responses. A rejected root key, throttling, a 500 or a network failure gets thrown instead, which is why the code above also has `app.onError`. Decide now whether an Unkey outage should fail closed with a 503, the way this code does, or fail open.

**Pass `permissions` if routes differ.** The middleware option takes a permission query that the key has to satisfy, and a key created without `items.read` gets a 403.

![A key without items.read gets 403 INSUFFICIENT_PERMISSIONS](/images/blog-images/api-key-authentication/02-insufficient-permissions-403.png)

### In any framework that speaks Request and Response

If you're not on Hono, or you want full control over each response, call `keys.verifyKey` yourself. The handler below is a plain `(Request) => Promise<Response>`, so it works in Next.js route handlers, Bun, Deno or Cloudflare Workers. We ran it with `Bun.serve`.

```ts
import { Unkey } from "@unkey/api";

const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? "" });

const STATUS: Record<string, number> = {
  NOT_FOUND: 401,
  DISABLED: 401,
  EXPIRED: 401,
  FORBIDDEN: 403,
  INSUFFICIENT_PERMISSIONS: 403,
  RATE_LIMITED: 429,
  USAGE_EXCEEDED: 402,
};

export async function handler(request: Request): Promise<Response> {
  const auth = request.headers.get("authorization") ?? "";
  const key = auth.startsWith("Bearer ") ? auth.slice("Bearer ".length) : "";
  if (!key) return Response.json({ error: "missing API key" }, { status: 401 });

  let data;
  try {
    ({ data } = await unkey.keys.verifyKey({ key, permissions: "items.read" }));
  } catch (err) {
    // bad root key, network failure, Unkey 5xx: fail closed
    console.error("unkey verify failed", err);
    return Response.json({ error: "authentication unavailable" }, { status: 503 });
  }

  if (!data.valid) {
    const headers = new Headers();
    if (data.code === "RATE_LIMITED") {
      const reset = data.ratelimits?.find((l) => l.exceeded)?.reset ?? Date.now();
      headers.set("Retry-After", String(Math.max(1, Math.ceil((reset - Date.now()) / 1000))));
    }
    return Response.json({ error: data.code }, { status: STATUS[data.code] ?? 401, headers });
  }

  return Response.json({ items: [], owner: data.identity?.externalId ?? data.keyId });
}
```

```ts
import { handler } from "./handler";

Bun.serve({ port: 3001, fetch: handler });
```

`keys.verifyKey` doesn't set `Retry-After` for you, so the handler works it out from the `reset` timestamp of whichever limit was exceeded.

![The plain handler returns 429 with a Retry-After header](/images/blog-images/api-key-authentication/05-plain-handler-retry-after.png)

In a fast burst of six requests during this run, the sixth came back 200 when we expected 429. The verifications right after it were `RATE_LIMITED` with `remaining: 0`. The docs say rate limit counts "sync across regions within moments, so `remaining` is approximate." Use the per-key limit to stop abuse, and don't rely on it for exact metering. If you need an exact count for billing, use credits, which the docs say change instantly.

## Step 4: Map verification results to HTTP status codes

`keys.verifyKey` returns HTTP 200 for every outcome, even for a key that doesn't exist.

![keys.verifyKey called directly with an unknown key returns NOT_FOUND with HTTP 200](/images/blog-images/api-key-authentication/03-raw-verify-200-not-found.png)

Your code should read `data.valid` first and then `data.code`, and pick the status your API returns from those. The table below comes from the [verifying keys](https://unkey.com/docs/api-management/keys/verifying-keys) docs.

| `data.code` | Meaning | Return to your caller |
|---|---|---|
| `VALID` | Every check passed | continue |
| `NOT_FOUND` | No such key, deleted keyspace, or your root key can't verify this keyspace | 401 |
| `DISABLED` | The key has `enabled: false` | 401 or 403 |
| `EXPIRED` | The key's `expires` has passed | 401 |
| `FORBIDDEN` | Client IP not on the keyspace allow list, or the workspace is disabled | 403 |
| `INSUFFICIENT_PERMISSIONS` | The `permissions` query wasn't satisfied | 403 |
| `RATE_LIMITED` | A rate limit on the key or its identity is exceeded | 429 |
| `USAGE_EXCEEDED` | Not enough credits | 402 or 429 |

Watch out for a missing root key permission. If your root key lacks `api.*.verify_key`, you get a 200 with `NOT_FOUND` instead of a permission error, and it looks exactly like every customer's key is wrong. When keys you just created come back `NOT_FOUND`, check the root key's permissions before anything else.

## Step 5: Limit what a key can do

You've already seen both pieces of this, `permissions` on the key and a permission query at verification time. The query language supports `AND`, `OR` and parentheses, with `AND` binding tighter, so you can write `documents.read AND (billing.read OR billing.write)`.

Once you have more than a couple of permissions, it's easier to group them into roles. This code creates a permission and a role, then gives the role to the key that got a 403 earlier.

```ts
import { Unkey } from "@unkey/api";

const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? "" });

await unkey.permissions.createPermission({ name: "items.write", slug: "items.write" });
await unkey.permissions.createRole({
  name: "blog-draft-editor",
  permissions: ["items.read", "items.write"],
});

const res = await unkey.keys.addRoles({
  keyId: process.argv[2],
  roles: ["blog-draft-editor"],
});
```

The response lists the role and the permissions it carries, and after that the same key got a 200 from `/items/list`. Roles behave differently from permissions here, because a role has to exist before you attach it or `createKey` fails. Your root key also needs RBAC permissions for these calls, and the [permission reference](https://unkey.com/docs/platform/root-keys/permissions) lists them.

Rate limits work the same way. You set `ratelimits` on `keys.createKey` and can change them later with `keys.updateKey` without a deploy. A limit on a key only counts requests made with that key. If one customer has several keys that should share the same allowance of requests, put the limit on their identity instead. Our rate limiting post [LINK: rate limit per customer post, not yet published] and the [key and identity limits](https://unkey.com/docs/api-management/ratelimiting/key-and-identity-limits) docs cover that in detail.

## Step 6: Rotate a key without breaking the customer

`keys.rerollKey` creates a new key with the same settings and keeps the old one working for a grace period you pick. We used 24 hours.

```bash
curl -X POST https://api.unkey.com/v2/keys.rerollKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{ "keyId": "key_auD1h0pde", "expiration": 86400000 }'
```

```json
{"data":{"key":"sk_live_AdSu…████","keyId":"key_8FdhLHY71"},"meta":{"requestId":"req_gPgdaKPxW"}}
```

As with `createKey`, you only see the new key once. It came with the old key's identity, metadata, permissions and rate limit, and our first request with it returned `"owner":"user_123","plan":"free"` with 4 of 5 requests remaining. The old key kept working too, and `keys.getKey` showed its `expires` had moved to 24 hours later, rounded to the minute.

![Disable returns 401 DISABLED, then a reroll: the old key is rate limited and its expires moves to about 24 hours later, and the new key returns 200 with remaining 4](/images/blog-images/api-key-authentication/06-disable-and-reroll.png)

_The 429 lines are the old key already at its limit. The new key's first 200 shows 4 of 5 remaining. `keys.getKey` on the old key shows `expires` about 24 hours later, rounded to the minute._

The [rerolling docs](https://unkey.com/docs/api-management/keys/rerolling-keys) also cover a few edge cases worth knowing.

- `expiration: 0` revokes the old key right away. Any other value gets rounded up to the next whole minute, so `1` can keep the old key alive for up to a minute.
- `expiration: null` leaves the old key's expiry as it was.
- The grace period applies even when the old key was due to expire sooner, so a reroll can make a key live longer.
- Analytics by `keyId` start from zero for the new key, while analytics by identity carry on.

In the dashboard, this is **Rotate key** in the key's actions menu. The grace period menu is revoke immediately, 15 minutes, 1 hour, 6 hours, 24 hours, or Do not expire original key. The dialog in the screenshot is a different key, `blog-draft-throwaway`, with 24 hours selected.

![The Rotate key dialog with the grace period dropdown open and 24 hours selected](/images/blog-images/api-key-authentication/auth-rotate-dialog.png)

## Step 7: Revoke a key

You can either disable a key or delete it. Disabling can be undone.

```ts
import { Unkey } from "@unkey/api";

const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? "" });

await unkey.keys.updateKey({ keyId: "key_jSF1UzeET", enabled: false });
```

After that, verification returns `DISABLED`. The other option is deleting the key.

```ts
await unkey.keys.deleteKey({ keyId: "key_jSF1UzeET" });
```

Once it's deleted, verification returns `NOT_FOUND`. `deleteKey` also takes an optional `permanent` flag, so check the [docs](https://unkey.com/docs/api-management/keys/enable-disable-delete) for what it changes before you rely on it.

**During an incident**, don't promise anyone an instant cutoff. According to the docs, a change to a key (disable, delete, new expiry, new permissions) "takes about 10 seconds to reach verification, and a few verifications just after that can still see the old state." We saw that happen. Right after the delete, one direct verification still reported the key as `DISABLED` before it switched to `NOT_FOUND`. Plan your runbook around a little more than 10 seconds.

## Let customers manage their own keys

The last item on the list is a page where customers manage their own keys. We have a hosted developer portal for this. You create a short-lived session for a signed-in user and redirect them to it. The SDK's types say scopes decide what the user sees, with `keys:read` and `keys:reroll` for the keys tab and `analytics:read` for their own usage. A user only ever sees their own keys and verifications.

## Document it in your OpenAPI spec

Clients and SDK generators need to know where to put the key. This part is plain OpenAPI and has nothing to do with Unkey. Declare a bearer scheme, and add an `apiKey` scheme if you also accept the key in a header. When you list them as separate entries under `security`, either one is accepted.

```yaml
openapi: 3.1.0
info:
  title: Items API
  version: 1.0.0
components:
  securitySchemes:
    bearerKey:
      type: http
      scheme: bearer
      description: "API key, sent as: Authorization: Bearer sk_live_..."
    headerKey:
      type: apiKey
      in: header
      name: X-API-Key
security:
  - bearerKey: []
  - headerKey: []
paths:
  /items/list:
    get:
      responses:
        "200": { description: "Items for the caller" }
        "401": { description: "Missing, unknown, disabled or expired key" }
        "403": { description: "Key lacks items.read" }
        "429": { description: "Rate limited. See Retry-After." }
```

The spec validates against OpenAPI 3.1 with `@apidevtools/swagger-parser`. If you want `apiKey` in a query parameter or a cookie, the [Security Scheme Object](https://spec.openapis.org/oas/v3.1.0#security-scheme-object) section of the spec shows how. If you accept `X-API-Key`, keep in mind that the `@unkey/hono` middleware and the handler above both read only the `Authorization` header by default. With the middleware, you pass a `getKey` function that reads your header instead.

## No code: check keys at the gateway

If your API runs on Unkey Compute, you can skip the middleware entirely. Add a **Key Auth** policy (app > **Policies** > **Add Policy** > **Key Auth**) and the gateway checks the key before the request reaches your code. The gateway answers rejected requests with a 401, 403 or 429, and your app never sees them.

We tested this on a Compute app with a Key Auth policy first and a Rate Limit policy second. Below is the Key Auth policy we ran. Because it sets no `locations`, the gateway reads the key from `Authorization: Bearer`.

```json
{
  "name": "Require a key",
  "enabled": true,
  "keyauth": {
    "keyspaces": ["ks_1234abcd"]
  }
}
```

A request with no key got a 401 `missing_credentials`, a made-up key got a 401 `invalid_key`, and a valid key reached the app. Policy changes only apply to the next deployment, and until we redeployed, requests without a key still got through.

**UNVERIFIED:** the docs also describe a `locations` list (a custom `header` with optional `stripPrefix`, or a `queryParam`), a `match` rule to scope the policy to paths, `permissionQuery`, and `credits`. We did not test any of these.

When a key passes, your app gets the caller in the `X-Unkey-Principal` header as JSON. In our test, `subject` was the identity's `externalId`, and `identity` and `source.key` (key ID, keyspace ID, name and meta) carried the rest. The docs say `subject` falls back to the key ID when there's no identity and that the gateway strips any `X-Unkey-*` header the client sends, so inside a Compute deployment the header can be trusted. We did not test those two points (UNVERIFIED). Run the same code locally and anyone can send it. The gateway also redacts the key from request logs (UNVERIFIED, from the docs).

## Other languages

Every language uses the same two calls, `keys.createKey` when a customer needs a key and `keys.verifyKey` on every request. The docs have framework guides for [Go](https://unkey.com/docs/api-management/guides/go), [Python](https://unkey.com/docs/api-management/guides/python), [Next.js](https://unkey.com/docs/api-management/guides/nextjs), [Express](https://unkey.com/docs/api-management/guides/express) and [Cloudflare Workers](https://unkey.com/docs/api-management/guides/cloudflare-workers), and the [quickstart](https://unkey.com/docs/api-management/get-started/quickstart) shows create and verify in curl, TypeScript, Go and Python side by side. If you already store hashed keys in your own database, [migrating keys](https://unkey.com/docs/api-management/keys/migrating-keys) imports the hashes so your customers keep the keys they have.

## If you build it yourself anyway

If you still want to roll your own, these are the parts that will bite you. Generate keys from a CSPRNG with at least 128 bits of randomness, and store only a hash. Compare keys in constant time. Strip keys from every log line, including the ones your reverse proxy writes. Support two valid keys per customer while they rotate, and make revocation a fast lookup so it doesn't wait on a cache expiry. After all that you still need per-key rate limiting, usage records and a UI for your customers. Each step in this post replaces one of those jobs with an API call.
