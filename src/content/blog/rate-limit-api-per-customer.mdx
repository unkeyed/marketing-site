Most rate limiting advice stops at "pick an algorithm and put a counter in Redis." That works until a customer creates a second API key and quietly doubles their quota, or a free tier customer spreads traffic across five keys, or sales promises a customer a higher limit and you have to ship code to give it to them.

The fix is knowing exactly what you're counting. "Per customer" and "per key" are two different limits, and most APIs that sell access need both. Below is how to set that up with Unkey from your own backend in TypeScript, and how to get the same result with no code if your API runs on Unkey Compute. Every response here came from a real test workspace. We prefixed test names with `blog-draft-`, so you'll see `blog-draft-cus_acme` in the output where the code says `cus_acme`.

## Per customer or per key: pick what you count

A **key limit** counts one API key on its own. A customer with three keys at 100 requests per minute each can make 300 requests a minute. You want that for a key with its own job, like a partner integration that syncs in bulk.

A **customer limit** counts every key that customer holds against one budget. Three keys, 100 requests per minute, shared. In Unkey, the customer is an *identity*. You create it with your own ID for the customer (`externalId`, say your Stripe customer ID), put the limit on it, and every key created with the same `externalId` draws from it.

You can use both. If a key and its identity both have a limit with the same name, the key's limit wins for that key. So the default is "everyone at Acme shares 1,000 requests a minute," and the exception is "except the partner sync key, which gets its own 5,000."

## Which algorithm to use

| Algorithm | How it counts | Trade-off |
|---|---|---|
| Fixed window | Counter per clock window, reset at the boundary | Simple, but allows up to twice the limit across a boundary |
| Sliding window | Weighs the previous window into the current count | Smooths the boundary burst, still cheap to store |
| Token bucket | Tokens refill at a steady rate, each request spends one | Allows controlled bursts, needs refill state per caller |

Key and identity limits in Unkey use a sliding window. The Compute gateway's rate limit policy, near the end, counts over a fixed window. How we keep counters across regions is in [How rate limiting works](https://www.unkey.com/docs/api-management/ratelimiting/how-it-works). The short version: counts are a close estimate, not exact, and windows of a minute or more are more accurate across regions. Need an exact monthly total? Use credits on the key. Those are exact.

You don't run Redis for any of this. We keep the counters.

## Step 1: Create a keyspace and a root key

In the dashboard, go to **Settings > Root Keys** and create a root key with these permissions:

- `api.*.create_api`, `api.*.create_key`, `api.*.verify_key`
- `identity.*.create_identity`, `identity.*.update_identity`
- `ratelimit.*.limit`, `ratelimit.*.create_namespace`, `ratelimit.*.set_override` (only for the section on limiting things that aren't keys)

Put it in `UNKEY_ROOT_KEY` on your server. Then create a keyspace for the keys you'll issue. The endpoint calls it an API:

```bash
curl -X POST https://api.unkey.com/v2/apis.createApi \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "my-api" }'
```

```json
{"data":{"apiId":"api_KDmiuuyC4"},"meta":{"requestId":"req_dVhtr8WrC"}}
```

Save the `apiId` as `UNKEY_API_ID`.

## Step 2: Create an identity for the customer with a shared limit

Do this when the customer signs up, with the limit for their plan:

```bash
curl -X POST https://api.unkey.com/v2/identities.createIdentity \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "cus_acme",
    "meta": { "plan": "free" },
    "ratelimits": [
      { "name": "requests", "limit": 100, "duration": 60000, "autoApply": true }
    ]
  }'
```

```json
{"data":{"identityId":"id_nLpkSl2sI"},"meta":{"requestId":"req_HBYqv6Nsx"}}
```

`duration` is the window in milliseconds. `autoApply: true` means every verification of every key this customer owns checks the limit, and your code never has to name it. `autoApply` is required. Leave it out and you get a 400:

```json
{"error":{"detail":"POST request body for '/v2/identities.createIdentity' failed to validate schema","errors":[{"location":"/properties/ratelimits/items/$ref/required","message":"missing property 'autoApply'"}],"status":400, ...}}
```

If you already created a key with this `externalId`, the identity exists and this call returns a 409. Use `identities.updateIdentity` (Step 5) instead.

## Step 3: Issue keys linked to that customer

Install the SDK with `npm install @unkey/api` and create a client once:

```ts
// unkey.ts
import { Unkey } from "@unkey/api";

export const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? "" });
```

Any key created with the same `externalId` links to the identity. Here the customer gets a production key and a staging key:

```ts
// create-keys.ts
import { unkey } from "./unkey";

for (const name of ["production", "staging"]) {
  const created = await unkey.keys.createKey({
    apiId: process.env.UNKEY_API_ID ?? "",
    prefix: "sk_live",
    externalId: "cus_acme",
    name,
  });
  // created.data.key is shown once. Hand it to the customer, store only the keyId.
  console.log(name, created.data.keyId, created.data.key);
}
```

We store a hash of the key, not the key itself. This is the only time you'll see `data.key`.

## Step 4: Verify the key and return 429 with headers

Your handler calls `keys.verifyKey` on every request. That one call checks the key and every auto-applied limit on the key and its identity. Two things catch people:

1. `keys.verifyKey` returns HTTP 200 for every outcome, including rate limited. Read `data.valid` and `data.code`.
2. It doesn't set response headers for you. Your server returns the 429 and copies the numbers onto it.

```ts
// server.ts
import { serve } from "@hono/node-server";
import { unkey } from "./unkey";

export async function handler(request: Request): Promise<Response> {
  const header = request.headers.get("authorization") ?? "";
  const key = header.startsWith("Bearer ") ? header.slice("Bearer ".length) : header;
  if (!key) return new Response("Missing API key", { status: 401 });

  const { data } = await unkey.keys.verifyKey({ key });

  // Report the shared "requests" budget on every response, allowed or not.
  const headers = new Headers();
  const rl = data.ratelimits?.find((r) => r.name === "requests");
  if (rl) {
    headers.set("X-RateLimit-Limit", String(rl.limit));
    headers.set("X-RateLimit-Remaining", String(rl.remaining));
    headers.set("X-RateLimit-Reset", String(Math.ceil(rl.reset / 1000))); // Unix seconds
  }

  if (data.code === "RATE_LIMITED") {
    const resetMs = data.ratelimits?.find((r) => r.exceeded)?.reset ?? Date.now();
    headers.set("Retry-After", String(Math.max(1, Math.ceil((resetMs - Date.now()) / 1000))));
    return new Response("Too many requests\n", { status: 429, headers });
  }
  if (data.code === "USAGE_EXCEEDED") {
    return new Response("Monthly quota exceeded\n", { status: 429, headers });
  }
  if (!data.valid) {
    return new Response("Unauthorized\n", { status: 401, headers });
  }

  return new Response(`hello ${data.identity?.externalId}\n`, { headers });
}

serve({ fetch: handler, port: 8787 });
```

`reset` comes back in Unix milliseconds. The handler converts it to seconds for `X-RateLimit-Reset`, which matches what the Compute gateway sends. It computes `Retry-After` in whole seconds with a floor of 1, as RFC 6585 expects. `USAGE_EXCEEDED` means the monthly quota (credits) ran out. That's a separate check from the rate limit.

Here's proof the budget is per customer. The production key makes 60 requests, the staging key makes 40, and the staging key's next request gets rejected. That key on its own has only been used 40 times:

![Two keys for the same customer share one 100 request budget. The 101st request returns 429 with Retry-After and X-RateLimit headers.](/images/blog-images/rate-limit-api-per-customer/shared-budget-429.png)

What if our rate limit check itself can't run? The docs are clear. Verification carries on as if the limits passed, so an outage never blocks valid keys. That's fail-open, and it's usually the right call for a limit that protects capacity rather than security. Remember it, because the gateway path further down makes the opposite choice.

## Step 5: Give a plan its own limit without a deploy

When Acme upgrades, update the identity. `ratelimits` replaces the whole list, so send every limit the customer should keep. This call raises `requests` to 1,000 per minute and adds an `exports` limit used in the next step:

```bash
curl -X POST https://api.unkey.com/v2/identities.updateIdentity \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "identity": "cus_acme",
    "meta": { "plan": "pro" },
    "ratelimits": [
      { "name": "requests", "limit": 1000, "duration": 60000, "autoApply": true },
      { "name": "exports", "limit": 5, "duration": 3600000, "autoApply": false }
    ]
  }'
```

`identity` takes either your `externalId` or Unkey's `identityId`. The response echoes the new state:

```json
{"data":{"externalId":"blog-draft-cus_acme","id":"id_nLpkSl2sI","meta":{"plan":"pro"},
 "ratelimits":[{"autoApply":true,"duration":60000,"id":"rl_LfQHGHlLy","limit":1000,"name":"requests"},
               {"autoApply":false,"duration":3600000,"id":"rl_SL54UjdTK","limit":5,"name":"exports"}]},
 "meta":{"requestId":"req_H2oVBQWJn"}}
```

No handler changes. No deploy. Every key Acme holds picks up the new numbers. The docs say this takes about 10 seconds. In our test, verifications showed the new 1,000 limit within a couple of seconds. But a verification that named the brand new `exports` limit right after the update still got a 412 from a node that hadn't seen it yet. So if a change adds a limit your code will name, change the identity first and ship the code that names it after.

Wire this to your billing webhook (subscription created, updated, cancelled) and plan limits stop being something engineers change by hand.

## Step 6: One expensive endpoint gets its own limit

Some endpoints cost far more to serve than others. You have two tools for that.

**A named limit that only applies where you ask for it.** The `exports` limit above has `autoApply: false`, so normal requests ignore it. The export endpoint names it at verification time. You can also charge a request more than one token with `cost`:

```bash
curl -X POST https://api.unkey.com/v2/keys.verifyKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "key": "sk_live_...", "ratelimits": [ { "name": "exports" }, { "name": "requests", "cost": 3 } ] }'
```

In the SDK that's `unkey.keys.verifyKey({ key, ratelimits: [{ name: "exports" }, { name: "requests", cost: 3 }] })`. All listed limits plus the auto-applied ones get checked together. If any one is exceeded, none of them is spent. Because `exports` lives on the identity, it's per customer too. In our test, Acme's first key used up the hour's five exports. A key Acme created after that was rate limited on its second export call, while plain requests on the same key kept working:

```text
### export 2
{"valid":false,"code":"RATE_LIMITED","ratelimits":[{"name":"requests","remaining":966,"exceeded":false},{"name":"exports","remaining":0,"exceeded":true}]}
### plain request after exports exhausted
{"valid":true,"code":"VALID","ratelimits":[{"name":"requests","remaining":969,"exceeded":false}]}
```

Name a limit that doesn't exist on the key or its identity and the whole call fails with HTTP 412 `err:unkey:application:precondition_failed`. A typo shows up right away.

**An exception for one key.** Give that key its own limit with the same name. It wins over the identity's limit for that key only:

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "apiId": "api_...",
    "prefix": "sk_live",
    "externalId": "cus_acme",
    "name": "partner-sync",
    "ratelimits": [ { "name": "requests", "limit": 5000, "duration": 60000, "autoApply": true } ]
  }'
```

Verifying that key showed `requests` at 5,000, while Acme's other keys still showed the shared 1,000.

There's also an inline form, where your code passes `limit` and `duration` inside the verification's `ratelimits` entry. It counts against the key only, never the identity. Be careful with it. A `limit` below 1 or a `duration` below 1000 isn't rejected. The verification silently skips every rate limit, auto-applied ones included. We sent `limit: 0` and got back `{"valid":true,"code":"VALID","ratelimits":null}`. Validate those numbers before you send them.

## Limiting things that aren't keys (IP, session, tenant)

Sign-up, login and password reset have no API key. For those, use the standalone limiter, `ratelimit.limit`. You pick a namespace (what you're limiting) and an identifier (who), and send the limit with each call:

```ts
// ip-limit.ts
import { unkey } from "./unkey";

export async function limitByIp(ip: string): Promise<Response | null> {
  const { data } = await unkey.ratelimit.limit({
    namespace: "signup",
    identifier: ip,
    limit: 5,
    duration: 60_000,
  });
  if (data.success) return null; // under the limit, carry on

  const retryAfter = Math.max(1, Math.ceil((data.reset - Date.now()) / 1000));
  return new Response("Too many requests", { status: 429, headers: { "Retry-After": String(retryAfter) } });
}
```

Calling it six times for the same IP:

```text
1 allowed
2 allowed
3 allowed
4 allowed
5 allowed
6 429 Retry-After=57
```

Like `keys.verifyKey`, it returns HTTP 200 either way, so read `data.success`. The first call with a new namespace name creates the namespace.

To give one identifier a different number without a code change, set an override. One catch we hit: the namespace has to exist first. Call `ratelimit.limit` on it at least once before setting an override, or `ratelimit.setOverride` returns 404 `ratelimit_namespace_not_found`.

```bash
curl -X POST https://api.unkey.com/v2/ratelimit.setOverride \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "namespace": "api.requests", "identifier": "cus_acme", "limit": 1000, "duration": 60000 }'
```

The code still sends `limit: 100`, but `cus_acme` now gets 1,000, and the response tells you an override applied:

![ratelimit.limit returns limit 1000 and an overrideId for the overridden identifier, and limit 100 for another identifier.](/images/blog-images/rate-limit-api-per-customer/override.png)

When one action has to pass several limits, say per user and per organization, `ratelimit.multiLimit` checks up to 100 in one call and counts them only if all pass:

```bash
curl -X POST https://api.unkey.com/v2/ratelimit.multiLimit \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    { "namespace": "api.requests", "identifier": "user_123", "limit": 100, "duration": 60000 },
    { "namespace": "api.requests", "identifier": "org_acme", "limit": 1000, "duration": 60000 },
    { "namespace": "llm.tokens", "identifier": "user_123", "limit": 50000, "duration": 3600000, "cost": 1200 }
  ]'
```

The response has `passed` for the whole call and one entry per check. When we sent a `cost` larger than the token budget, `passed` was `false`. In that case none of the checks count, including the ones that passed.

## Rate limiting at the gateway with no code

> We ran this setup on a test Compute app with the CLI's `gateway set-policies`, using the same policy body with a limit of 5 per minute. Key Auth first and Rate Limit second worked as described, and the sixth request got the 429 shown below. We did not send the raw HTTP call below, and we did not test the fail-closed behaviour (UNVERIFIED).

If your API runs on Unkey Compute, the gateway verifies keys and enforces limits before a request ever reaches your app. Add policies under **Policies > Add Policy** in the app, or set them with the API:

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "my-project",
    "app": "api",
    "environment": "production",
    "policies": [
      {
        "name": "Require a key",
        "enabled": true,
        "keyauth": { "keyspaces": ["ks_..."] }
      },
      {
        "name": "100 per minute per customer",
        "enabled": true,
        "ratelimit": {
          "limit": 100,
          "windowMs": 60000,
          "identifiers": [{ "authenticatedSubject": {} }]
        }
      }
    ]
  }'
```

How this maps to everything above:

- The **Key Auth** policy behaves like `keys.verifyKey`, so the identity and key limits from Steps 2 to 6 are already enforced by it.
- The **Rate Limit** policy is an extra cap. `authenticatedSubject` is the identity's `externalId` when the key has one (otherwise the key ID), so it counts per customer. It uses a fixed window.
- Order matters. The rate limit has to come after key auth, or every request counts as `unknown`.
- Policy changes apply to the next deployment, so redeploy after saving. The root key needs `environment.*.set_policies`.
- The gateway sets `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (Unix seconds) and, on a 429, `Retry-After`.
- If rate limiting itself fails at the gateway, the request gets a 500 instead of going through (UNVERIFIED, from the docs). That's fail-closed, the opposite of `keys.verifyKey`. Pick the path whose failure mode you can live with.

## What clients see, and how they should retry

A rate-limited client from the handler above gets:

```text
HTTP/1.1 429 Too Many Requests
retry-after: 5
x-ratelimit-limit: 100
x-ratelimit-remaining: 0
x-ratelimit-reset: 1791919680
```

`Retry-After` is the number to obey. A good client waits that long, adds a little jitter so clients limited at the same moment don't all come back at once, and gives up after a few attempts. No header? Fall back to exponential backoff:

```ts
// client.ts
export async function fetchWithRetry(url: string, init: RequestInit = {}, maxRetries = 3): Promise<Response> {
  for (let attempt = 0; ; attempt++) {
    const res = await fetch(url, init);
    if (res.status !== 429 || attempt >= maxRetries) return res;

    const retryAfter = Number(res.headers.get("Retry-After"));
    const baseMs = Number.isFinite(retryAfter) && retryAfter > 0 ? retryAfter * 1000 : 2 ** attempt * 1000;
    const jitterMs = Math.random() * 250; // spread out clients that were limited together
    await new Promise((resolve) => setTimeout(resolve, baseMs + jitterMs));
  }
}
```

Against a customer limited to 3 requests per 5 seconds, five calls in a row (with a log line added to the retry branch):

![The client gets 429 on its fourth call, waits about 2 seconds as Retry-After says, and succeeds.](/images/blog-images/rate-limit-api-per-customer/client-retry.png)

If you ship an SDK, put this in it. Most 429 storms come from clients retrying immediately in a loop.

## Checklist

- Put the main limit on the identity so all of a customer's keys share it. Link keys with `externalId`.
- Give a single key an exception with a key limit of the same name.
- Change plan limits with `identities.updateIdentity`. No deploy.
- Use `autoApply: false` named limits or `cost` for expensive endpoints.
- Use `ratelimit.limit` with overrides for anything that isn't a key, and `multiLimit` when one action must pass several limits.
- Return 429 with `Retry-After` yourself when you call `keys.verifyKey`. The Compute gateway sets it for you.
- Know your failure mode: `keys.verifyKey` fails open, the gateway rate limit policy fails closed.

If you want the reference docs, start with the [per-user rate limit cookbook](https://www.unkey.com/docs/api-management/cookbook/per-user-rate-limit) and the [key and identity limits reference](https://www.unkey.com/docs/api-management/ratelimiting/key-and-identity-limits).
