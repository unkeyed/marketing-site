Most rate limiting advice tells you to pick an algorithm, put a counter in Redis, and stops there. That holds up until a customer creates a second API key and quietly doubles their quota. It also breaks when a free tier customer spreads traffic across five keys, or when sales promises a customer a higher limit and an engineer has to ship code to give it to them.

What fixes it is deciding what you count. A limit per customer and a limit per key are different things, and most APIs that sell access need both. Below is how to set both up with Unkey from your own TypeScript backend, then the same thing with no code if your API runs on Unkey Compute.

## Decide whether you count per customer or per key

A **key limit** counts each API key separately. A customer with three keys at 100 requests per minute each can send 300 requests a minute in total. You want that when a key has its own job, like a partner integration that syncs data in bulk.

A **customer limit** counts every key the customer holds toward the same number. With three keys and a limit of 100 requests per minute, all three keys share those requests. In Unkey the customer is called an _identity_. You create it with your own ID for that customer in `externalId` (your Stripe customer ID works well), attach the limit to it, and every key you create with the same `externalId` counts against that limit.

You can use both. When a key and its identity each have a limit with the same name, the key's own limit applies to that key. Everyone at Acme can share 1,000 requests a minute while the partner sync key gets 5,000 of its own.

## Which algorithm to use

| Algorithm      | How it counts                                           | Trade-off                                                  |
| -------------- | ------------------------------------------------------- | ---------------------------------------------------------- |
| Fixed window   | Counter per clock window, reset at the boundary         | Simple, but allows up to twice the limit across a boundary |
| Sliding window | Weighs the previous window into the current count       | Smooths the boundary burst, still cheap to store           |
| Token bucket   | Tokens refill at a steady rate, each request spends one | Allows controlled bursts, needs refill state per caller    |

Unkey uses a sliding window for key and identity limits. The rate limit policy on the Compute gateway, near the end, counts over a fixed window instead. We keep counters in several regions, and [How rate limiting works](https://www.unkey.com/docs/api-management/ratelimiting/how-it-works) explains how. In practice `remaining` is a close estimate. When one region sees most of an identifier's traffic, enforcement is tight. When traffic is split across regions, a short burst can get through in more than one region before the counts catch up. If you need an exact total, put credits on the key. Credits are counted exactly.

You don't need to run Redis for any of this. We keep the counters for you.

## Step 1: Create a keyspace and a root key

In the dashboard, open **Root Keys** and create a root key with the permissions below.

- `api.*.create_api`, `api.*.create_key`, `api.*.verify_key`
- `identity.*.create_identity`, `identity.*.update_identity`
- `ratelimit.*.limit`, `ratelimit.*.create_namespace`, `ratelimit.*.set_override` (you only need these for the section on limiting things that aren't keys)

Store it as `UNKEY_ROOT_KEY` on your server. Next, create a keyspace to hold the keys you'll hand out. The endpoint calls that keyspace an API.

```bash
curl -X POST https://api.unkey.com/v2/apis.createApi \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "my-api" }'
```

```json
{ "data": { "apiId": "api_KDmiuuyC4" }, "meta": { "requestId": "req_dVhtr8WrC" } }
```

Save the `apiId` from the response as `UNKEY_API_ID`.

## Step 2: Create an identity for the customer with a shared limit

Create the identity when the customer signs up, and give it the limit their plan includes.

```bash
curl -X POST https://api.unkey.com/v2/identities.createIdentity \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "cus_acme",
    "meta": { "plan": "free" },
    "ratelimits": [
      { "name": "requests", "limit": 100, "duration": 60000, "autoApply": true }
    ]
  }'
```

```json
{ "data": { "identityId": "id_nLpkSl2sI" }, "meta": { "requestId": "req_HBYqv6Nsx" } }
```

`duration` is the length of the window in milliseconds. With `autoApply: true`, every verification of every key this customer owns checks the limit, and your code never has to mention it by name. You have to send `autoApply`. The API returns a 400 if it's missing.

```json
{"error":{"detail":"POST request body for '/v2/identities.createIdentity' failed to validate schema","errors":[{"location":"/properties/ratelimits/items/$ref/required","message":"missing property 'autoApply'"}],"status":400, ...}}
```

If you've already created a key with this `externalId`, the identity already exists and this call returns a 409. Use `identities.updateIdentity` instead, which Step 5 covers.

## Step 3: Issue keys linked to that customer

Install the SDK and create one client you can import everywhere.

```bash
npm install @unkey/api
```

```ts
// unkey.ts
import { Unkey } from '@unkey/api';

export const unkey = new Unkey({ rootKey: process.env.UNKEY_ROOT_KEY ?? '' });
```

Any key you create with the same `externalId` links to that identity. In this example the customer gets one key for production and one for staging.

```ts
// create-keys.ts
import { unkey } from './unkey';

for (const name of ['production', 'staging']) {
  const created = await unkey.keys.createKey({
    apiId: process.env.UNKEY_API_ID ?? '',
    prefix: 'sk_live',
    externalId: 'cus_acme',
    name,
  });
  // created.data.key is shown once. Hand it to the customer, store only the keyId.
  console.log(name, created.data.keyId, created.data.key);
}
```

We only store a hash of the key, so this response is the only time you'll ever see `data.key`.

## Step 4: Verify the key and return 429 with headers

Your handler calls `keys.verifyKey` on every request. That one call checks the key itself and every auto-applied limit on both the key and its identity. Two details catch people.

1. `keys.verifyKey` returns HTTP 200 for every outcome, even when the key is rate limited, so you have to read `data.valid` and `data.code`.
2. It doesn't set any response headers. Your server sends the 429 and copies the limit numbers onto it.

```ts
// server.ts
import { serve } from '@hono/node-server';

import { unkey } from './unkey';

export async function handler(request: Request): Promise<Response> {
  const header = request.headers.get('authorization') ?? '';
  const key = header.startsWith('Bearer ') ? header.slice('Bearer '.length) : header;
  if (!key) return new Response('Missing API key', { status: 401 });

  const { data } = await unkey.keys.verifyKey({ key });

  // Report the shared "requests" budget on every response, allowed or not.
  const headers = new Headers();
  const rl = data.ratelimits?.find((r) => r.name === 'requests');
  if (rl) {
    headers.set('X-RateLimit-Limit', String(rl.limit));
    headers.set('X-RateLimit-Remaining', String(rl.remaining));
    headers.set('X-RateLimit-Reset', String(Math.ceil(rl.reset / 1000))); // Unix seconds
  }

  if (data.code === 'RATE_LIMITED') {
    const resetMs = data.ratelimits?.find((r) => r.exceeded)?.reset ?? Date.now();
    headers.set('Retry-After', String(Math.max(1, Math.ceil((resetMs - Date.now()) / 1000))));
    return new Response('Too many requests\n', { status: 429, headers });
  }
  if (data.code === 'USAGE_EXCEEDED') {
    return new Response('Monthly quota exceeded\n', { status: 429, headers });
  }
  if (!data.valid) {
    return new Response('Unauthorized\n', { status: 401, headers });
  }

  return new Response(`hello ${data.identity?.externalId}\n`, { headers });
}

serve({ fetch: handler, port: 8787 });
```

`reset` comes back in Unix milliseconds. The handler turns it into seconds for `X-RateLimit-Reset` so it matches what the Compute gateway sends. `Retry-After` here is whole seconds and never lower than 1. RFC 6585 defines the 429 status and that header. `USAGE_EXCEEDED` is a different check from the rate limit. It means the customer has used up their monthly credits quota.

We tested this with both of Acme's keys. The production key made 60 requests and the staging key made 40. The next request from the staging key was rejected, even though that key had only been used 40 times. Every key Acme holds counts toward the same limit.

## Step 5: Change a customer's limit without a deploy

When Acme upgrades, you update the identity. Sending `ratelimits` replaces the entire list, so include every limit the customer should keep. This call raises `requests` to 1,000 per minute and adds an `exports` limit the next step uses.

```bash
curl -X POST https://api.unkey.com/v2/identities.updateIdentity \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "identity": "cus_acme",
    "meta": { "plan": "pro" },
    "ratelimits": [
      { "name": "requests", "limit": 1000, "duration": 60000, "autoApply": true },
      { "name": "exports", "limit": 5, "duration": 3600000, "autoApply": false }
    ]
  }'
```

The `identity` field accepts either your `externalId` or Unkey's `identityId`. The response shows the identity after the change.

```json
{
  "data": {
    "externalId": "cus_acme",
    "id": "id_nLpkSl2sI",
    "meta": { "plan": "pro" },
    "ratelimits": [
      {
        "autoApply": true,
        "duration": 60000,
        "id": "rl_LfQHGHlLy",
        "limit": 1000,
        "name": "requests"
      },
      {
        "autoApply": false,
        "duration": 3600000,
        "id": "rl_SL54UjdTK",
        "limit": 5,
        "name": "exports"
      }
    ]
  },
  "meta": { "requestId": "req_H2oVBQWJn" }
}
```

You don't touch the handler. You don't deploy anything. Every key Acme holds picks up the new numbers on its own. Plan changes reach verifications within about 10 seconds. Right after an update that adds a brand new named limit, a verification that asks for that name by name can still get a 412 from a node that hasn't seen it yet. Update the identity first, then ship the code that uses the new name.

If you call this from your billing webhook when a subscription is created, updated, or canceled, nobody on your team has to change plan limits by hand again.

## Step 6: Give an expensive endpoint its own limit

Some endpoints cost a lot more to serve than others. You have two ways to handle them.

**A named limit that only applies where you ask for it.** The `exports` limit above has `autoApply: false`, so ordinary requests never check it. Your export endpoint asks for it by name when it verifies the key. You can also charge a single request more than one token with `cost`.

```bash
curl -X POST https://api.unkey.com/v2/keys.verifyKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "key": "sk_live_...", "ratelimits": [ { "name": "exports" }, { "name": "requests", "cost": 3 } ] }'
```

The SDK version looks like this:

```ts
unkey.keys.verifyKey({ key, ratelimits: [{ name: 'exports' }, { name: 'requests', cost: 3 }] });
```

The limits you list and the auto-applied ones are all checked together. If any one of them is over, none of them gets spent. Since `exports` lives on the identity, every key the customer holds shares it too. In our test, Acme's first key used up all five exports for the hour. Acme then created another key, and that key was rate limited on its second export call while its ordinary requests kept working.

```text
### export 2
{"valid":false,"code":"RATE_LIMITED","ratelimits":[{"name":"requests","remaining":966,"exceeded":false},{"name":"exports","remaining":0,"exceeded":true}]}
### plain request after exports exhausted
{"valid":true,"code":"VALID","ratelimits":[{"name":"requests","remaining":969,"exceeded":false}]}
```

If you name a limit that doesn't exist on the key or its identity, the whole call fails with HTTP 412 `err:unkey:application:precondition_failed`. You find out about typos right away.

**An exception for one key.** Give that key its own limit with the same name, and it replaces the identity's limit for that key alone.

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "apiId": "api_...",
    "prefix": "sk_live",
    "externalId": "cus_acme",
    "name": "partner-sync",
    "ratelimits": [ { "name": "requests", "limit": 5000, "duration": 60000, "autoApply": true } ]
  }'
```

When we verified that key, `requests` came back at 5,000. Acme's other keys still showed the 1,000 they share.

You can also pass `limit` and `duration` inline, inside the verification's `ratelimits` entry. An inline limit only counts against the key and never the identity. Be careful with it. The API doesn't reject a `limit` below 1 or a `duration` below 1000. The verification silently skips every rate limit instead, including the auto-applied ones. We sent `limit: 0` and got back:

```json
{ "valid": true, "code": "VALID", "ratelimits": null }
```

Check those numbers in your own code before you send them.

## Limiting things that aren't keys (IP, session, tenant)

Sign-up, login, and password reset happen before anyone has an API key. For those you use the standalone limiter, `ratelimit.limit`. You choose a namespace for the thing you're limiting and an identifier for who is doing it, then send the limit along with each call.

```ts
// ip-limit.ts
import { unkey } from './unkey';

export async function limitByIp(ip: string): Promise<Response | null> {
  const { data } = await unkey.ratelimit.limit({
    namespace: 'signup',
    identifier: ip,
    limit: 5,
    duration: 60_000,
  });
  if (data.success) return null; // under the limit, carry on

  const retryAfter = Math.max(1, Math.ceil((data.reset - Date.now()) / 1000));
  return new Response('Too many requests', {
    status: 429,
    headers: { 'Retry-After': String(retryAfter) },
  });
}
```

We called it six times for the same IP.

```text
1 allowed
2 allowed
3 allowed
4 allowed
5 allowed
6 429 Retry-After=57
```

It returns HTTP 200 whether the call is allowed or not, just like `keys.verifyKey`, so check `data.success`. The first call that uses a new namespace name creates that namespace.

To give one identifier a different number without changing code, set an override. We hit one snag doing this. The namespace has to exist before you can override anything in it. Call `ratelimit.limit` on it at least once first, or `ratelimit.setOverride` returns 404 `ratelimit_namespace_not_found`.

```bash
curl -X POST https://api.unkey.com/v2/ratelimit.setOverride \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "namespace": "api.requests", "identifier": "cus_acme", "limit": 1000, "duration": 60000 }'
```

The code still sends `limit: 100`, but `cus_acme` now gets 1,000. The response includes the override so you can tell it applied.

```text
### setOverride (namespace now exists)
{"data":{"overrideId":"rlor_w3lLwQY6v"},"meta":{"requestId":"req_q17UvNS2H"}}
### override applied on poll 1
{"data":{"limit":1000,"overrideId":"rlor_w3lLwQY6v","remaining":999,"reset":1793214060000,"success":true},"meta":{"requestId":"req_6PGyrLeS4"}}
### other identifier, same call
{"data":{"limit":100,"remaining":99,"reset":1793214060000,"success":true},"meta":{"requestId":"req_qOl7u4kpS"}}
```

Sometimes one action has to pass several limits, for example one per user and one per organization. `ratelimit.multiLimit` checks up to 100 of them in a single call and only counts them if every one passes.

```bash
curl -X POST https://api.unkey.com/v2/ratelimit.multiLimit \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    { "namespace": "api.requests", "identifier": "user_123", "limit": 100, "duration": 60000 },
    { "namespace": "api.requests", "identifier": "org_acme", "limit": 1000, "duration": 60000 },
    { "namespace": "llm.tokens", "identifier": "user_123", "limit": 50000, "duration": 3600000, "cost": 1200 }
  ]'
```

The response has a `passed` field for the whole call plus one entry per check. When we sent a `cost` bigger than the token limit allowed, `passed` came back `false`. None of the checks were counted, including the ones that passed on their own.

## Rate limiting at the gateway with no code

If your API runs on Unkey Compute, the gateway checks keys and enforces limits before a request ever gets to your app. Add policies in the app under **Policies > Add Policy**, or set them through the API.

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "my-project",
    "app": "api",
    "environment": "production",
    "policies": [
      {
        "name": "Require a key",
        "enabled": true,
        "keyauth": { "keyspaces": ["ks_OyAFjLBtw"] }
      },
      {
        "name": "5 per minute per caller",
        "enabled": true,
        "ratelimit": {
          "limit": 5,
          "windowMs": 60000,
          "identifiers": [{ "authenticatedSubject": {} }]
        }
      }
    ]
  }'
```

How the gateway lines up with the earlier steps.

- The **Key Auth** policy works the same way as `keys.verifyKey`, so it already enforces the identity and key limits from Steps 2 to 6.
- The **Rate Limit** policy adds a second limit on top. `authenticatedSubject` resolves to the identity's `externalId` when the key has one and to the key ID when it doesn't, so it counts per customer. It counts over a fixed window.
- Put the rate limit after key auth. If it runs first, every request counts as `unknown`.
- Policy changes take effect on the next deployment, so redeploy after you save them. The root key needs `environment.*.set_policies`.
- The gateway sends `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (in Unix seconds) on its responses, plus `Retry-After` on a 429.
- If rate limiting itself fails at the gateway, the request gets a 500 instead of going through. That's fail-closed, the opposite of `keys.verifyKey`. Pick the path whose failure mode you can live with.

## What clients see, and how they should retry

A client that hits the limit in the handler above gets this response.

```text
HTTP/1.1 429 Too Many Requests
retry-after: 5
x-ratelimit-limit: 100
x-ratelimit-remaining: 0
x-ratelimit-reset: 1791919680
```

Clients should wait for the number of seconds in `Retry-After`. A well-behaved client waits that long, adds a little random jitter so clients limited at the same moment don't all retry together, and gives up after a few attempts. If the header is missing, it falls back to exponential backoff.

```ts
// client.ts
export async function fetchWithRetry(
  url: string,
  init: RequestInit = {},
  maxRetries = 3,
): Promise<Response> {
  for (let attempt = 0; ; attempt++) {
    const res = await fetch(url, init);
    if (res.status !== 429 || attempt >= maxRetries) return res;

    const retryAfter = Number(res.headers.get('Retry-After'));
    const baseMs =
      Number.isFinite(retryAfter) && retryAfter > 0 ? retryAfter * 1000 : 2 ** attempt * 1000;
    const jitterMs = Math.random() * 250; // spread out clients that were limited together
    await new Promise((resolve) => setTimeout(resolve, baseMs + jitterMs));
  }
}
```

We pointed it at a customer limited to 3 requests per 5 seconds and made five calls in a row, with a log line added to the retry branch.

```bash
$ API_KEY=... npx tsx client.ts   # customer limit: 3 requests per 5 seconds
1 200 remaining=2
2 200 remaining=1
3 200 remaining=0
429, retrying in 3.1s
4 200 remaining=0
5 200 remaining=1
```

If you ship an SDK, build this retry logic into it. Most floods of 429s come from clients that retry immediately in a loop.

## Where to see who is getting limited

Every verification and every `ratelimit.limit` call ends up in analytics. The dashboard shows it in a few places.

- The identity page lists each request as Valid or Ratelimited, with the key id and the region. Rejected verifications (including rate limited ones) show up here.
- **Edit ratelimit** on that identity holds the named limits. The dialog may need a scroll to show every rule.
- Filtering **Outcome is RATE_LIMITED** leaves the rejected requests.
- Under **Ratelimit** in the sidebar, open a namespace and its **Overrides** page to see identifiers that have a different limit.

## Checklist

- Put the main limit on the identity so all of a customer's keys share it, and link keys to it with `externalId`.
- Give a single key an exception with a key limit of the same name.
- Change plan limits with `identities.updateIdentity` instead of deploying code.
- Use `autoApply: false` named limits or `cost` for expensive endpoints.
- Use `ratelimit.limit` with overrides for anything that isn't a key, and `multiLimit` when one action must pass several limits.
- When you call `keys.verifyKey`, return the 429 and `Retry-After` yourself. The Compute gateway sets them for you.
- Remember that `keys.verifyKey` fails open and the gateway rate limit policy fails closed.

If you want the reference docs, start with the [per-user rate limit cookbook](https://www.unkey.com/docs/api-management/cookbook/per-user-rate-limit) and the [key and identity limits reference](https://www.unkey.com/docs/api-management/ratelimiting/key-and-identity-limits).
