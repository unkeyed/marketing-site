# Deploy an API with preview environments and request logs

When you ship a public API, you need somewhere to run it and a preview for each pull request. You also need to check who is calling, and you want logs for the day something breaks. We'll set all of that up on Unkey by connecting a GitHub repository. Every push deploys the app, Compute runs it, and API Management issues and checks the keys. Unkey also records each request the app serves.

## What you'll have at the end

You get a production URL on `unkey.app` that updates when you push to your default branch, and a preview URL for every other branch and fork pull request. The gateway checks API keys and rate limits each caller, and you get logs and metrics without adding an SDK.

You need a Compute plan before the first deploy. The dashboard asks you to **Choose a Compute plan**, and only a workspace admin can pick one.

## The sample API

Any language works as long as the process listens on `PORT`, which Unkey sets to the configured port (8080 by default). I'm using a small Hono app.

{/* prettier-ignore */}
```js
// index.js
import { Hono } from "hono";
import { serve } from "@hono/node-server";

const app = new Hono();

app.get("/healthz", (c) => c.text("ok"));

app.get("/v1/hello", (c) => {
  // Set by the gateway after a key-auth policy verifies the caller.
  const raw = c.req.header("x-unkey-principal");
  const principal = raw ? JSON.parse(raw) : null;
  return c.json({
    hello: principal?.subject ?? "anonymous",
    deployment: process.env.UNKEY_DEPLOYMENT_ID ?? "local",
  });
});

app.get("/whoami", (c) => {
  const raw = c.req.header("x-unkey-principal");
  return c.json({ principal: raw ? JSON.parse(raw) : null });
});

const port = Number(process.env.PORT ?? 8080);
serve({ fetch: app.fetch, port });
console.log(`listening on ${port}`);
```

Run it locally once without a principal header and once with one.

```
$ curl -s localhost:8080/v1/hello
{"hello":"anonymous","deployment":"local"}
$ curl -s localhost:8080/v1/hello -H 'X-Unkey-Principal: {"version":"v1","subject":"acme","type":"API_KEY","source":{"key":{"keyId":"key_123","keySpaceId":"ks_123","meta":{}}}}'
{"hello":"acme","deployment":"local"}
```

Unkey sets `UNKEY_DEPLOYMENT_ID` on every instance, so each response tells you which deployment answered it.

## Step 1: Connect the repository and deploy

### From the dashboard

1. Open **Projects** and choose **Create project**, then enter a **Project Name**. Unkey generates the **Slug** from the name, and that slug is what the API and CLI use. The new project opens on an empty Apps list.

![The Create New Project dialog with Project Name and Slug fields](/images/blog-images/deploy-api-previews-monitoring/gh-create-project-2x.png)

2. Choose **Create app**. The wizard opens on **Deploy a new app** and asks where the code comes from. Choose **GitHub repository**. This step doesn't ask for a name or a slug. The first time you do this in a workspace, GitHub asks you to install the Unkey GitHub App and grant it repository access.

![Deploy a new app, with GitHub repository as the source](/images/blog-images/deploy-api-previews-monitoring/deploy-create-app-2x.png)

Then pick the repository. You choose the branch on the next step.

![The Import a GitHub repository step listing the account's repositories](/images/blog-images/deploy-api-previews-monitoring/gh-repo-picker-2x.png)

3. **Set up your app** asks for a name and a branch, then shows the build, scaling, and environment variables. This one is named `api`, on `main`, with an automatic build at `./` and one instance in four regions. Environment variables start empty. Choose **Edit** there to add a key and a value. You can mark a value sensitive, and the environment dropdown chooses Production or Preview. The dialog here is set to Preview.

![The Set up your app step: name api, branch main, automatic build, one instance in four regions](/images/blog-images/deploy-api-previews-monitoring/gh-configure-2x.png)

![The Environment variables dialog scoped to the Preview environment](/images/blog-images/deploy-api-previews-monitoring/gh-configure-2-2x.png)

4. The Build row is an automatic build at `./`. Point the root at a subdirectory for a monorepo, and add a watch path such as `services/api/**` when pushes that miss that path should be recorded as `skipped`. Environment variables are scoped per environment. If you mark a secret as sensitive, it stays write-only.

5. Choose **Deploy**. The deployment moves through `pending`, `starting`, `building`, `deploying`, `network` (shown as **Assigning Domains**), and `finalizing` until it is `ready`. The build log streams during `building`.

![A deployment building from main, with the build log open](/images/blog-images/deploy-api-previews-monitoring/gh-building-2x.png)

The deployment page shows the branch and commit it came from, and Unkey builds that commit straight from the repository.

![The same deployment at Ready, Show URLs open, with one instance in each of four regions](/images/blog-images/deploy-api-previews-monitoring/gh-ready-2x.png)

A new app starts at port 8080 with 0.25 vCPU and 256 MiB. This one is running one instance in each of four regions.

### From the API or CLI

Every call is a `POST` to `https://api.unkey.com/v2/{service}.{procedure}` with a root key in `Authorization: Bearer`.

`projects.createProject` creates the project. `apps.createApp` connects the repo when the body includes `"git":{"repository":"owner/repo"}`. Unkey fills in `defaultBranch` from the repository.

```bash
curl -X POST https://api.unkey.com/v2/deployments.createDeployment \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" -H "Content-Type: application/json" \
  -d '{"project":"my-project","app":"api","environment":"production","git":{"branch":"main"}}'
```

That returns `201` and a deployment id, which you poll with `deployments.getDeployment`. On a small app the status moves through `building` and `deploying` to `ready` in about 30 seconds. The app is then live at `https://<project>-<app>-<workspace>.unkey.app`.

`POST /v2/deployments.createDeployment` is deprecated in favor of `POST /v3/deployments.createDeployment`. On v3, `oci.image` replaces `image.dockerImage`.

![getDeployment for a production deployment built from the main branch, status ready, with its unkey.app domains](/images/blog-images/deploy-api-previews-monitoring/01-deploy-ready-2x.png)

A ready deployment lists the git branch, the commit, and its domains. You get the live domain, an environment domain, a branch domain, a commit domain, and one pinned to that deployment.

Install the CLI with `npm install -g unkey` and export `UNKEY_ROOT_KEY`. The same four calls are `unkey api projects create-project`, `unkey api apps create-app --git='{"repository":"owner/repo"}'`, `unkey api deployments create-deployment --git='{"branch":"main"}'`, and `unkey api deployments get-deployment`.

If the image is already in a registry, `unkey deploy docker.io/traefik/whoami:v1.10.3 --project=my-project --app=api --env=production` deploys it. That image listens on port 80, so set the app port first with `unkey api apps update-settings --port=80`. The command prints `Deployment completed successfully` and finishes in about 9 seconds.

A workspace builds one deployment at a time, and the rest wait in `pending`. Production jumps ahead of preview, so a fix doesn't sit behind pull request builds. If a deployment waits an hour it fails, and you can deploy it again once the queue has drained.

## Step 2: Every branch and pull request gets a preview

Once the repository is connected, a push to the default branch deploys production. A push to any other branch creates a preview with its own branch domain. Each one shows up in GitHub as a deployment, and Unkey keeps a single pull request comment updated with a **Visit Preview** link.

![The app's Deployments list filtered to Preview, showing the Add /whoami route preview](/images/blog-images/deploy-api-previews-monitoring/gh-preview-list-2x.png)

Open a preview deployment to see its branch, commit, environment, and domains.

![A preview deployment for Add /whoami route, with its branch, commit, Preview environment, and domains](/images/blog-images/deploy-api-previews-monitoring/gh-preview-detail-2x.png)

Fork pull requests get extra care, because their code would run with your preview variables, including database URLs and third-party keys. A fork pull request waits in `awaiting_approval` until a project member approves it in the dashboard. GitHub shows a failing **Unkey Deploy Authorization** check ("Awaiting authorization from a project member") while it waits. Pushes from people with write access skip that check.

Give the preview environment its own values. Point it at a test database and test-mode payment keys, and maybe a separate keyspace so preview keys cannot call production.

You don't have to clean up previews yourself, because Unkey stops them in these cases.

| Trigger                                                           | What stops                                    | When              |
| ----------------------------------------------------------------- | --------------------------------------------- | ----------------- |
| New preview deployment on the same branch                         | The deployment that was on that branch domain | 1 minute later    |
| Preview deployment gets no requests                               | That deployment                               | After 1 hour idle |
| You stop it (**Stop deployment** or `deployments.stopDeployment`) | That deployment                               | Right away        |

A stopped preview answers `503` with `err:frontline:capacity:deployment_offline`. Wake it with **Wake deployment** or `deployments.startDeployment`. It goes through `deploying` and back to `ready`. You cannot start one while the workspace is suspended by its Compute spend budget.

![Stop and wake the preview: whoami goes 200, then 503 deployment_offline, then 200 again once it is ready](/images/blog-images/deploy-api-previews-monitoring/02-preview-2x.png)

## Step 3: Require an API key and add a rate limit at the gateway

Every Compute app sits behind the gateway. Policies run there, before the request reaches your code. Start with a keyspace and a key from API Management. The API calls a keyspace an API.

```bash
curl -X POST https://api.unkey.com/v2/apis.createApi \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "my-api" }'
```

The response includes `apiId`. Save it, because you need it every time you create a key.

Create a key for a customer. `externalId` links the key to an identity, so that customer's keys count as one subject.

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"apiId":"api_...","prefix":"pay","externalId":"acme","name":"acme laptop","meta":{"plan":"pro"}}'
```

`data.key` is the full key, and this response is the only time you get it. Unkey stores a hash, so hand the key to the customer now.

The gateway wants the keyspace id (`ks_...`). If you pass the API id (`api_...`) instead, the call returns 404 and says the keyspace does not exist. Both ids are on the keyspace **Settings** page. `keys.verifyKey` returns the keyspace id as `keyspaceId`.

Next, set the production policies. They run from top to bottom. Put the rate limit after the key check, or every request is counted as `unknown`. Five a minute is enough to see it trip. In production, start nearer 100. The root key needs `environment.*.set_policies`. In the dashboard, use **Policies > Add Policy > Key Auth**, then **Rate Limit**.

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "my-project",
    "app": "api",
    "environment": "production",
    "policies": [
      { "name": "Require a key", "enabled": true,
        "keyauth": { "keyspaces": ["ks_..."] } },
      { "name": "5 per minute per caller", "enabled": true,
        "ratelimit": { "limit": 5, "windowMs": 60000,
                       "identifiers": [{ "authenticatedSubject": {} }] } }
    ]
  }'
```

A deployment keeps the image, variables, and policies it was created with. Saving a policy does nothing to the one that is already live, so redeploy from the deployment page. The new policies then take a moment to reach every domain.

With the new deployment live, a request with no key gets `401` `missing_credentials`. A bad key gets `401` `invalid_key`. Past the limit, the caller gets `429` `rate_limited` and `Retry-After`. Responses also include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` in Unix seconds.

![Calls to the production domain: 401 with no key, 401 with a bad key, then 404s while the rate limit counts down, and 429 on the sixth request](/images/blog-images/deploy-api-previews-monitoring/03-key-auth-ratelimit-2x.png)

Those `404`s are `page not found` because the calls hit `/`, and this app has no `/` route.

A rejected request never reaches your code. One that gets through arrives with an `X-Unkey-Principal` header. On the preview, `/whoami` with no key returns 401, and a valid key returns that header as JSON.

![/whoami on the preview returns 401 with no key, and the principal JSON with a valid key](/images/blog-images/deploy-api-previews-monitoring/04-principal-2x.png)

`subject` is the identity's `externalId`, or the key id when the key has no identity. `authenticatedSubject` counts by that value, so one customer's keys share a limit. The gateway strips any `X-Unkey-*` header the client sends. Compute deployments are only reachable through the gateway, so the header inside Compute is the one Unkey set. If you run the same code somewhere else, a caller can forge it.

Preview has its own policy list. If a preview should not be public, set policies for it too, or choose **All Environments** in the dashboard.

## Step 4: Watch requests, logs and metrics

You don't install anything for this, because Unkey records the traffic for you.

Open **Requests** to see the request log. It has one row for each request that reached your app, with the method, host, path, status, region, deployment, instance, and latency split into `gateway_latency` and `instance_latency`.

![The project Requests view filtered to api, with GET /health 200 and its deployment details open](/images/blog-images/deploy-api-previews-monitoring/gh-requests-2x.png)

Runtime logs live under **Logs**. They are stdout and stderr from every instance, with the severity parsed out.

The app **Overview** charts Requests/s and Errors/s. This one is Live, with 175 requests this hour, four regions, 0.25 vCPU, and 256 MiB.

![The app Overview page with Requests/s and Errors/s, status, regions, and resources](/images/blog-images/deploy-api-previews-monitoring/gh-metrics-2x.png)

The deployment page has a Network map with one instance in each of four regions.

![The deployment page Network map, one instance in each of four regions](/images/blog-images/deploy-api-previews-monitoring/gh-network-2x.png)

Build logs show the steps and output from the image build. You see them on the deployment page while it is building.

A policy rejection never reaches the app, so it is missing from the request log. The key check still shows up in API Management's verification analytics, next to your own `keys.verifyKey` calls.

`analytics.getGatewayRequests` runs SQL against `gateway_requests_v1`. The root key needs the wildcard `project.*.read_gateway_requests`.

```bash
curl -X POST https://api.unkey.com/v2/analytics.getGatewayRequests \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"SELECT path, count() AS requests, avg(total_latency) AS avg_latency FROM gateway_requests_v1 WHERE time >= toUnixTimestamp64Milli(now64(3) - INTERVAL 1 HOUR) GROUP BY path ORDER BY requests DESC LIMIT 10"}'
```

A query that hits data returns `200`, and rows show up about 20 seconds after the traffic. The body has one object per path, with its count and latency.

```json
{
  "data": [{ "path": "/healthz", "requests": "<count>", "avg_latency": "<ms>" }]
}
```

Queries only cover the last 7 days. Ask for anything older and the API returns `400` `query_range_exceeds_retention`.

Runtime logs are a different call, `analytics.getRuntimeLogs` on `runtime_logs_v1`. The root key needs its own runtime-logs read permission, `project.*.read_runtime_logs`. The gateway-requests permission does not cover them.

To keep logs longer, or to use your own tools, a log drain forwards one stream (gateway HTTP requests, runtime logs, key verifications, rate limits, or audit logs) to an HTTPS endpoint or an Axiom dataset. Every plan starts with a log drain limit of 0, so ask support to raise it.

## How this compares with GitHub Actions plus Cloud Run, ECS or Kubernetes

The other setups leave more of this to you. Each provider column links to that provider's docs.

| Step                                 | Unkey                                                                        | [GitHub Actions + Cloud Run](https://docs.cloud.google.com/run/docs/deploying)                                                                             | [GitHub Actions + ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/update-service-console-v2.html) | [GitHub Actions + Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) |
| ------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Deploy on push                       | Connect the repo and it's built in                                           | Workflow runs `gcloud run deploy`                                                                                                                          | Workflow registers a task definition and updates the service                                                       | Workflow applies manifests or sets the image                                                         |
| Preview per branch or PR             | Built-in, with a branch domain and fork approval                             | Workflow deploys a revision with `--no-traffic --tag` to get a tagged URL ([docs](https://cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)) | Not covered in the linked docs. You script a service per PR                                                        | Not covered in the linked docs. You script a namespace or release per PR                             |
| Clean up previews                    | Auto-stop after 1 hour idle, or 1 minute after a newer preview on the branch | You remove tags or revisions yourself                                                                                                                      | Your workflow tears down what it created                                                                           | Your workflow tears down what it created                                                             |
| API key auth and per-key rate limits | Gateway policies backed by API Management keys                               | A separate gateway or code in your app                                                                                                                     | A separate gateway or code in your app                                                                             | An ingress or gateway add-on, or code in your app                                                    |
| Request logs                         | Built-in, plus SQL via the analytics API                                     | Cloud Logging                                                                                                                                              | CloudWatch, if you configure it                                                                                    | Whatever logging stack you run                                                                       |

Render's [service previews](https://render.com/docs/service-previews) are the closest built-in match for the preview row. You choose **Manual** or **Automatic** pull request previews, and Render deletes a preview when its pull request is merged or closed. Unkey also puts a gateway in front of production and previews, and the request log is queryable.

## Cost

API Management and Compute are billed separately. You can use either one without the other. Prices below are from [unkey.com/pricing](https://www.unkey.com/pricing).

API Management's Free tier includes 150,000 valid requests a month, 1,000 API keys, and 1 day of log retention. Invalid requests, including rate-limited calls and bad keys, do not count toward that quota. Audit logs on Free are kept for 3 days.

Compute has three plans. Each one includes a monthly usage credit equal to the fee. Until December 31, 2026, the first month is discounted. Starter costs $0 the first month and $5 after that, Pro costs $20 and then $25, and Business costs $45 and then $50. On Starter, credit left over from that first month carries to the next bill. Unused credits otherwise do not roll over.

|                         | Starter       | Pro           | Business        |
| ----------------------- | ------------- | ------------- | --------------- |
| Monthly fee             | $5            | $25           | $50             |
| First month             | $0            | $20           | $45             |
| Usage credit each month | $5            | $25           | $50             |
| Max per instance        | 2 vCPU, 2 GiB | 8 vCPU, 8 GiB | 16 vCPU, 32 GiB |
| Instances per region    | 4             | 8             | 16              |
| Custom domains          | 1             | Unlimited     | Unlimited       |
| Log retention           | 3 days        | 7 days        | 14 days         |
| Team members            | None          | Unlimited     | Unlimited       |

Every plan allows one concurrent build, git push to deploy, and a preview for each pull request. Preview usage is billed at the same rates as production.

Past the included credit, you pay for the vCPU and memory you actually use, the disk you allocate, egress, and active keys checked by a Compute key auth policy. CPU is billed while your code is running. The rates below are rounded.

| Meter       | Rate                     |
| ----------- | ------------------------ |
| vCPU        | about $0.025 per hour    |
| Memory      | about $9 per GB-month    |
| Disk        | about $0.16 per GB-month |
| Egress      | $0.05 per GB             |
| Active keys | $2 per 1,000 per month   |

If the default instance (0.25 vCPU, 256 MiB) ran flat out all month, you'd pay about $4.50 for CPU and $2.25 for memory, so about $6.75, and the Starter credit covers most of that. Treat that as the most it could cost. A real API almost never keeps CPU and memory at 100 percent around the clock, so your bill will land well under it. We bill the CPU and memory you actually use, averaged over time, not what you configured, and CPU only counts while your code is running. Time spent waiting on I/O or sitting idle between requests isn't billed.

You can cap the bill with a monthly budget.

- Set it in whole dollars under **Settings > Billing**. Only a workspace admin can change it.
- Admins get an email the first time month-to-date spend crosses 50, 75, and 100 percent.
- **Stop workloads at the budget** is off until you turn it on. At 100 percent, running deployments stop and every request gets `402` `spend_limit_reached`.
- Remove the budget, turn the stop option off, or wait for the next month, and the live deployment comes back without a redeploy. Raising the budget resumes compute once spend has stayed under the new budget for two checks in a row.
- Nothing is deleted.
