You have an API running on your machine. Hosting it means that process gets a public URL and TLS, so other people can call it.

This guide follows one path. A GitHub repository with a Dockerfile deploys on Unkey Compute. API Management then issues a key, and a gateway policy rate limits each caller.

[Compute](https://www.unkey.com/docs/compute) builds the image, runs the container, and puts a gateway in front of every deployment. [API Management](https://www.unkey.com/docs/api-management/get-started/quickstart) is where the keys live. This post uses both on the same API.

## What API hosting means

Hosting is a process with a hostname and a certificate. On Unkey the process is a container. Compute builds it from your Dockerfile and runs it.

Every deployment sits behind the gateway. With no policies, the gateway forwards the request. A key check and a rate limit are policies, and they apply on the next deployment.

## Can I host an API for free?

Starter is $5 a month and includes $5 of usage. Through December 31, 2026, the first month is $0 and then $5, from a $5 credit. On Starter, credit left from that offer carries to the next bill.

## What to check before you deploy

Only a workspace admin can pick the plan. If the workspace has none, the first deploy opens a dialog titled Choose a Compute plan. Caps for each plan are on [Compute plans](https://www.unkey.com/docs/compute/get-started/plans).

The process has to listen on `PORT`. Unkey sets that variable to the environment's port, 8080 unless you change it, and that value overrides any `ENV PORT` in the image. The process has to exit on `SIGTERM` so an instance can drain when it is replaced.

Writes on the container's own filesystem stay under 128 MiB. Anything larger goes on the disk at `/data`. The contract is on [Dockerfile builds](https://www.unkey.com/docs/compute/build/dockerfile).

Environment variables belong to one environment. Production and preview can hold different values for the same key, and every value is encrypted. Mark a secret Sensitive and it becomes write-only: you can replace or delete it, and you cannot read it back.

A running deployment keeps the variables it was created with. Save, then redeploy. The rules are on [Environment variables](https://www.unkey.com/docs/compute/configure/environment-variables).

Compute runs in `us-west-2` (Oregon), `us-east-1` (Northern Virginia), `eu-central-1` (Frankfurt), and `ap-southeast-1` (Singapore). Each environment picks from one to five of those, and the deployment runs in all of them.

A new app in the dashboard starts in every region available to the workspace, at 0.25 vCPU, 256 MiB, and one instance in each. Frankfurt is the only European region. See [Regions](https://www.unkey.com/docs/build-and-deploy/regions).

A `ready` deployment gets `unkey.app` hostnames on its own. A custom domain is optional. Starter includes one, and Pro and Business include unlimited custom domains. Add it on Domains and publish the DNS records shown there.

## Deploy from GitHub with a Dockerfile

The server on this path is the container. Put a Dockerfile in the repo, connect GitHub, and push. A registry image is deployed from [Deploy a container image](https://www.unkey.com/docs/compute/get-started/deploy-an-image), and a Node API without its own Dockerfile is covered in [How to ship a Node.js API or backend](/blog/git-push).

Every example below uses the project `payments` and the app `api`. The build context is the repository root unless you set a root directory.

Open Projects, create `payments`, and on Deploy a new app pick GitHub repository. Install the Unkey GitHub App if the workspace has not. Click the repo, then under Build choose the Dockerfile.

The branch starts as the repository's default branch. Dashboard steps are on [Deploy from GitHub](https://www.unkey.com/docs/compute/get-started/deploy-from-github). Saving Build writes the Dockerfile path to production and preview.

To set production on its own, send `dockerfile` with `environments.updateSettings`. The root key goes in `Authorization: Bearer`. Field rules are on [Build settings](https://www.unkey.com/docs/compute/configure/build-settings).

```bash
curl -X POST https://api.unkey.com/v2/environments.updateSettings \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "payments",
    "app": "api",
    "environment": "production",
    "dockerfile": "Dockerfile"
  }'
```

Choose Deploy. Unkey builds a production deployment from the head of the branch. Wait until the status is `ready`.

In a workspace named `acme`, that app answers on `payments-api-acme.unkey.app`. A later push to the default branch creates the next production deployment. The production domains move to it once that deployment is `ready`.

A failed build shows the error on the deployment page. [Dockerfile builds](https://www.unkey.com/docs/compute/build/dockerfile) explains the usual causes.

## Add API keys

Create the keys in API Management, then attach the keyspace to `api` with a key auth policy and redeploy. The gateway checks the key before the container sees the request.

Open Keyspaces (APIs) and create a keyspace. Settings shows two IDs.

`keys.createKey` takes the API ID (`api_...`). The gateway policy takes the keyspace ID (`ks_...`). See [Keyspaces](https://www.unkey.com/docs/api-management/keyspaces/overview).

Create the root key under Settings > Root Keys with `api.*.create_key`. `data.key` is shown once. This is the [quickstart](https://www.unkey.com/docs/api-management/get-started/quickstart) request.

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "apiId": "api_...",
    "name": "My first key"
  }'
```

On the `api` app, open Policies and add a Key Auth policy with that keyspace ID. With no location set, the gateway reads `Authorization: Bearer`.

Save, then redeploy. The live deployment keeps the policies it was created with.

A missing or rejected key gets `401`, `403`, or `429`, and the app does not see the request. A key that passes arrives with `X-Unkey-Principal` set, so the app can tell who called. Outcomes are on [API key authentication](https://www.unkey.com/docs/compute/gateway/api-key-auth). The header fields are on [The principal header](https://www.unkey.com/docs/compute/gateway/principal).

Those same keys work if your code calls `keys.verifyKey` and the API runs somewhere else. Issuing them, and that verify call, are in [How to add API key authentication to your API without building a key system](/blog/api-key-authentication).

## Add a rate limit

A rate limit policy counts requests in a window and rejects the rest before they reach the app. In the dashboard, add a policy and set the type to Rate Limit. The form starts at 100 requests per 60 seconds per client IP.

This API already requires a key, so count the caller, and place the rate limit after key auth. If it runs first, the gateway has no caller yet and those requests share one counter.

The call below is the [gateway policies](https://www.unkey.com/docs/compute/gateway/policies) example, using `payments` and `api`. It requires a key, then allows 100 requests a minute for that caller. `windowMs` is the window in milliseconds.

`gateway.setPolicies` replaces the environment's whole list. If `api` already has policies, read them first and include them, or this call removes them. The root key needs `environment.*.set_policies`.

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "payments",
    "app": "api",
    "environment": "production",
    "policies": [
      {
        "name": "Require a key",
        "enabled": true,
        "keyauth": { "keyspaces": ["ks_1234abcd"] }
      },
      {
        "name": "100 per minute per key",
        "enabled": true,
        "ratelimit": {
          "limit": 100,
          "windowMs": 60000,
          "identifiers": [{ "authenticatedSubject": {} }]
        }
      }
    ]
  }'
```

Redeploy after you save. Replacing the list resets the counters once the next deployment is live. Over the limit, the caller gets `429` `rate_limited` and the app does not see the request. The response headers are on [Rate limit policy](https://www.unkey.com/docs/compute/gateway/rate-limiting).

`authenticatedSubject` is the identity's external ID when the key has an identity, so that customer's keys share one counter. A key with no identity is counted by its key ID.

A shared customer budget, including a different limit on one key, is [How to rate limit an API per customer or per API key](/blog/rate-limit-api-per-customer). Limits on the key itself, and `ratelimit.limit` for a route with no key, are on [Rate limiting](https://www.unkey.com/docs/api-management/ratelimiting/overview).

## Preview deployments

A push to any branch other than the default creates a preview deployment and a branch URL. A pull request from a fork stays in `awaiting_approval` until a project member approves it.

A preview with no requests stops after one hour idle. Preview is billed the same as production. See [Production and preview](https://www.unkey.com/docs/compute/concepts/production-and-preview).

## Logs

The build log streams on the deployment page while the image builds.

Lines the process writes to stdout or stderr show up under Logs. See [Runtime logs](https://www.unkey.com/docs/compute/observe/runtime-logs).

Requests that reached the app are under Requests. A request the gateway rejected is absent there, because the app never handled it. See [Request logs](https://www.unkey.com/docs/compute/observe/requests).

Figures are from the [pricing page](https://www.unkey.com/pricing), which lists Compute as Unkey Deploy. There is no trial. You choose the plan.

Through December 31, 2026, the first month is $0 then $5 on Starter, $20 then $25 on Pro, and $45 then $50 on Business. Included credit offsets compute, storage, egress, and active keys.

Past the credit, memory is billed on the average the instance used. CPU is billed while the code is executing. An active key is one verified at least once that month through a Key Auth policy on Deploy. Unit rates are on the pricing page.

An admin can set a monthly spend budget under Settings > Billing. With the stop option on, hitting the budget suspends compute. Deployments stop, and the gateway answers `402` `spend_limit_reached`. Raising or removing the budget, or turning the stop off, brings compute back.

API Management is a separate bill. The free tier is $0, with 150,000 valid requests a month and 1,000 API keys. Rate-limited calls and bad keys sit outside that quota. The tier does not deploy the API.

## FAQ

### Can I host an API for free?

The free API Management tier does not run the container. Compute hosting starts on Starter, at $5 a month with $5 of included usage.

### What is hosting an API?

Callers reach the API on a hostname over TLS. Compute runs the container, and the gateway is in front of it.

### How do I deploy a REST API on a server?

Connect the GitHub repository to the `payments` project, set the Dockerfile on `api`, and choose Deploy. Wait for `ready`, then add the key policy and the rate limit and redeploy.
