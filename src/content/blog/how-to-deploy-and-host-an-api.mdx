The hard part is not the handler. A public URL, a key check, and a rate limit should not cost a weekend of glue.

We run that as one path. Push a repo with a Dockerfile to Unkey Compute. The key and its rate limit live in API Management, and the gateway enforces both before your code runs. With no policies, the gateway forwards the request. A key check is a policy, and it applies on the next deployment.

## Three things before you push

1. Only a workspace admin can pick the Compute plan. If the workspace has none, the first deploy opens a dialog titled Choose a Compute plan.
2. The process has to listen on `PORT`. We set that to the environment's port, 8080 unless you change it, and it overrides any `ENV PORT` in the image.
3. The process has to exit on `SIGTERM`, so an instance can drain when we replace it.

Disk and the rest of that contract are on [Dockerfile builds](https://www.unkey.com/docs/compute/build/dockerfile).

Compute runs in four regions today: Oregon (`us-west-2`), Northern Virginia (`us-east-1`), Frankfurt (`eu-central-1`), and Singapore (`ap-southeast-1`). A new app starts with one instance in each region the workspace can use. You can change that list per environment. It accepts one to five names, even though only four exist right now, and every deployment in the environment runs in all of them.

## One root key for the curls

An admin opens Root Keys in the sidebar and creates the key before the curls below. We show the secret once. If Root Keys is missing from the sidebar, the account is not an admin.

The curls below need `api.*.create_key` and `environment.*.set_policies`. The CI deploy also needs `environment.*.create_deployment`. You can narrow each one, `api.<api_id>.create_key` or the same idea for a single environment. [Root key permissions](https://www.unkey.com/docs/platform/root-keys/permissions) is the full catalog, including the longer resource names if you want a key that can only touch one app.

## Push the Dockerfile

The examples use a project slug of `payments`, an app slug of `api`, and a workspace named `acme`. That production URL is `payments-api-acme.unkey.app`. If your slugs differ, use those instead.

Open Projects, create `payments`, and on Deploy a new app pick the GitHub repository. Install the Unkey GitHub App if the workspace hasn't. The dashboard names the app after the repo.

The branch starts as the repository's default branch. Open App settings > Build and pick the Dockerfile from the list we found in the repo, or type the path. Saving there writes it for production and preview. Connecting the repo is on [Deploy from GitHub](https://www.unkey.com/docs/compute/get-started/deploy-from-github).

Choose Deploy. We build a production deployment from the head of that branch. Wait until the status is `ready`.

A later push to the default branch creates the next production deployment. Once that one is `ready`, it becomes the live deployment and the production domains move to it. If the status is `failed`, the deployment page shows the error.

### CI deploys with one call

The dashboard is the path. If the deploy itself has to come from CI, it is one call, and this one is v3. Every other call below is v2.

```bash
curl -X POST https://api.unkey.com/v3/deployments.createDeployment \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "payments",
    "app": "api",
    "environment": "production",
    "git": { "branch": "main" }
  }'
```

`main` is the branch in this example. Pass the branch you actually want built. The call returns a deployment id and the build runs after that. Wait for `ready` the same way.

## Keys get checked before your code runs

Open Keyspaces (APIs) and create a keyspace. The sidebar still says APIs. Same object. The API calls it an API, as in `apis.createApi`. The gateway calls it a keyspace.

Settings shows two IDs, and they are not interchangeable. `keys.createKey` wants the API ID, the one that starts with `api_`. The gateway policy wants the keyspace ID, the one that starts with `ks_`. Copy both. Mixing them up is a bad afternoon.

## Limit the caller, not the IP

A gateway rate limit that runs before the key check has no caller yet. Every anonymous request shares one counter, including people who never had a key. Put the limit on the key, and run the key check first, so the count belongs to that key.

Five requests a minute is small on purpose, so you can watch it trip. `autoApply` means every verification counts against this limit. Leave it out and the call fails with a 400.

```bash
curl -X POST https://api.unkey.com/v2/keys.createKey \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "apiId": "api_...",
    "name": "My first key",
    "ratelimits": [
      { "name": "requests", "limit": 5, "duration": 60000, "autoApply": true }
    ]
  }'
```

`duration` is the window in milliseconds, so `60000` is a minute. The key comes back once, in `data.key`. Store it. That string is the bearer token below.

On the `api` app, add a Key Auth policy with the `ks_` id. With no location set, the gateway reads `Authorization: Bearer`.

Same step from the API. This call replaces the environment's whole policy list.

:::warn Replaces the whole list

`gateway.setPolicies` replaces the environment's whole list. If `api` already has policies, read them first and include them here, or this call removes them.

:::

```bash
curl -X POST https://api.unkey.com/v2/gateway.setPolicies \
  -H "Authorization: Bearer $UNKEY_ROOT_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "project": "payments",
    "app": "api",
    "environment": "production",
    "policies": [
      {
        "name": "Require a key",
        "enabled": true,
        "keyauth": { "keyspaces": ["ks_..."] }
      }
    ]
  }'
```

A running deployment keeps the policies, variables, and settings it was created with. Deploy again after you save. The next deployment is the one that checks keys. That is the only extra deploy in this path.

## The sixth request is a 429

No key:

```bash
curl -sS -w "\n%{http_code}\n" https://payments-api-acme.unkey.app/
```

The status is 401. The body is:

```json
{
  "error": {
    "code": "err:frontline:client:missing_credentials",
    "message": "Authentication required. Please provide a valid API key."
  }
}
```

With the key, on a fresh window:

```bash
curl -sS -D - -o /dev/null -w "%{http_code}\n" https://payments-api-acme.unkey.app/ \
  -H "Authorization: Bearer $KEY"
```

That is a 200. The app sees the request, and it arrives with `X-Unkey-Principal` set, so the handler can tell who called. The response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. Limit is the 5 you put on the key. Remaining is how many of those are left in the window. The body is whatever your API returns.

That call used one of the five. Four more still pass. The next one does not.

```bash
for i in 1 2 3 4 5; do
  curl -sS -o /dev/null -w "%{http_code}\n" https://payments-api-acme.unkey.app/ \
    -H "Authorization: Bearer $KEY"
done
```

```text
200
200
200
200
429
```

The 429 includes `Retry-After`, in whole seconds, and this body:

```json
{
  "error": {
    "code": "err:frontline:client:rate_limited",
    "message": "Rate limit exceeded. Please try again later."
  }
}
```

Which failure is which, in the order the gateway stops:

- No key in any location the policy checks: `401` `err:frontline:client:missing_credentials`.
- The key does not exist, is disabled or expired, the workspace is disabled, or the key is from a keyspace the policy does not list: `401` `err:frontline:client:invalid_key`. The caller cannot tell those apart.
- The key fails a permission query: `403` `err:frontline:client:insufficient_permissions`.
- The key's rate limit is used up: `429` `err:frontline:client:rate_limited`.
- The key is out of credits: `429` `err:frontline:client:usage_exceeded`.

The outcomes are on [API key authentication](https://www.unkey.com/docs/compute/gateway/api-key-auth).

## Your code doesn't run the rejected request

The gateway sends the 401 and the 429. Your process does not run. Those requests still show up in Unkey's request logs, so you get the full picture.

## What this actually costs you

This isn't free. Compute starts at $5 a month, and that $5 is usage credit.

Until December 31, 2026, your first month on Starter is free. After that it's $5. Unused promo credit rolls over.

You pay for the CPU and memory the app actually uses, not the ceiling you configured. Memory the instance is holding is billed even between requests. Time spent waiting on I/O does not count as active CPU. Idle is not free.

The free API Management tier issues keys. It does not run the container. Pro, Business, and the API Management tiers are on the [pricing page](https://www.unkey.com/pricing).
